# Stochastic variability and fault injection

Status: normative, implementation contract. This section is the single source of truth for how randomness works in twinflow. Every other subsystem spec references it rather than restating it. ## Normative rules

Other specs cite these by number.

- **R1. Reproducible, not predictable.** One run seed governs every stochastic stream through a splittable RNG with per-subsystem child seeds. Applying D-05, the guarantee has two tiers and this document never states the stronger one alone. On one pinned platform with one pinned dependency set, identical seed plus identical resolved config yields a byte-identical event log. Across platforms, the business events are identical and the continuous fields agree inside a tolerance derived from measured divergence. Neither tier constrains the shape of the variability, which is heavy and realistic.
- **R2. Correct support, not clamping.** A quantity's distribution family is chosen so its support is already the physical support. Durations use lognormal, gamma, or Weibull. Bounded ratios use scaled beta. Counts use Poisson or negative binomial. Inter-arrival times use exponential, or a non-homogeneous Poisson process where a time-of-day or seasonal profile applies.
- **R3. No tail truncation and no sigma cap anywhere.** Rare extreme values are real and are retained. With genuine heavy tails the control charts must distinguish a rare common-cause tail draw from a real special cause, which is the hard problem in statistical process control and the skill this repo exists to demonstrate.
- **R4. Physical invariants are assertions, never clamps.** They live in the property-based test suite. A violation means the distribution choice is wrong, and CI fails loudly rather than production rounding silently.
- **R5. Common cause and special cause are generated separately and recorded separately.** Common-cause variation comes from `config/distributions.yaml`. Special-cause variation comes from a materialised fault schedule. Nothing is both at once except the two declared boundary cases in section D.
- **R6. Faults transform samples; they never consume subsystem draws.** A fault changes a parameter or post-processes a value. It never adds or removes a draw from a subsystem stream, and it draws its own randomness from its own stream.
- **R7. Ground truth is sideband.** Fault labels are written to `runs/<run_id>/ground_truth/`. They are never published to a UNS topic, never written to a historian table that a detector reads, and never present in any dataset exported for model training unless the export is explicitly labelled as supervised.
- **R8. Every stochastic quantity appears in this catalog with a config key.** No numeric distribution parameter is written as a literal in application code. CI enforces this with a lint rule over the sampler and subsystem packages.
- **R9. Every statistic this section asserts names an external published reference.** Applying D-11, a gate over a value taken from a published source is never checked more tightly than that source printed it, a gate over a stochastic quantity states a measured noise floor and sets its tolerance above it, and every gate states the result that would falsify it. This repository is never a reference for itself. A statistic with no valid external reference is recorded as an open question in section G and never as a passing gate. Section F.7 holds the registry.
- **R10. Every test tier states a runtime budget, and the budget is itself tested.** Applying D-13, a scenario that grows past the job budget fails as a defect rather than as a timeout. Section F.7 holds the budget table and the arithmetic test.
- **R11. A component whose output steers the simulation draws deterministically or leaves the tape.** Applying D-04, a solver is bounded by a deterministic budget rather than by wall-clock seconds, and a learned model runs behind the `Inference` port with a pinned artefact hash. Section A.8 states the contract.

## A. RNG architecture

### A.1 The mechanism

Chosen mechanism: **numpy `SeedSequence` with content-addressed spawn keys, feeding `PCG64DXSM` bit generators**.

A stream is identified by a dotted **stream name**, not by a position. The derivation is fixed byte for byte, because D-06 makes it a cross-language contract rather than a Python implementation detail:

```
digest      = blake2b(stream_name.encode("utf-8"),
                      digest_size=16,
                      person=b"twinflow-rng")          # 12 bytes, zero-padded to 16
spawn_key   = (w0, w1, w2, w3)                          # four uint32, little-endian, from digest
entropy     = uint32[4] = (base_seed & 0xFFFFFFFF,
                           base_seed >> 32,
                           replication_index & 0xFFFFFFFF,
                           replication_index >> 32)
seed_seq    = numpy.random.SeedSequence(entropy=entropy, spawn_key=spawn_key)
generator   = numpy.random.Generator(numpy.random.PCG64DXSM(seed_seq))
```

`base_seed` is a uint64 recorded in the hashed core of the run manifest, per E.1. `replication_index` is a uint64 that distinguishes replications of the same scenario; folding it into the root entropy rather than into the stream name gives each replication an independent tree while keeping stream names stable across replications.

Four details in that block are load-bearing, and each one is a place where a reasonable-looking implementation silently produces different numbers.

1. **The personalization string is padded, not truncated.** The BLAKE2b parameter block fixes the personalization field at 16 bytes, and the Python standard library pads a shorter value with zeros, so the 12-byte string and the same string followed by four zero bytes are one value (B.13 ref 23). Any second implementation pads the same way or produces a different digest for every stream name.
2. **The entropy is a fixed-width uint32 array, never a tuple of Python integers.** numpy converts a non-negative integer to as many uint32 words as its magnitude needs, so `(base_seed, replication_index)` yields between two and four words depending on how large the seed happens to be, and the mixing path changes with it. A uint32 array is passed through unchanged, which pins the assembled entropy at exactly four words for every seed (numpy source, `numpy/random/bit_generator.pyx`, `_coerce_to_uint32_array` and `get_assembled_entropy`, v2.3.0, retrieved 2026-08-09, HTTP 200).
3. **Four entropy words means no zero-fill.** numpy pads the run entropy to `pool_size` with zeros when a spawn key is present and the entropy is shorter than the pool. Fixing the entropy at four words, which is `DEFAULT_POOL_SIZE`, makes the padding branch unreachable and removes a version-sensitive behaviour from the contract.
4. **The pool size stays at the default 4.** That is a 128-bit entropy pool, and `generate_state` cycles the pool words through the output hash, so a different pool size changes every stream.

Why this and not the alternatives:

- **Why not `SeedSequence.spawn(n)`.** `spawn` is positional: it extends the parent's spawn key by the child's index and maintains an `n_children_spawned` counter, so the child a subsystem receives depends on how many subsystems spawned before it. Adding subsystem 40 to the registration sequence shifts subsystem 1's child if registration order changes, and every recorded run and golden file breaks. Content-addressed spawn keys remove the ordering dependency. The name is the address.
- **Why not `PCG64` itself.** `PCG64` is numpy's current default, and it was this section's first choice. numpy documents a statistical weakness in it: a pair of `PCG64` streams whose lower 58 state bits agree fails PractRand when interleaved, a seeded increment adds no protection against that particular weakness, and the stated guidance is that thousands of streams are comfortable while millions are the point to consider `PCG64DXSM` (B.13 ref 15). This section's declared ceiling of 750,000 streams sits between those two ranges, near enough to the warning that it is a decision rather than an assumption. A.1a computes what each choice costs. The switch was taken on 2026-08-09, before the known-answer corpus of A.7 existed, because the price is zero until that corpus is frozen and rises the day a second language is tested against it. Open question G.11 holds the record.
- **Why not `PCG64DXSM.jumped(k)`.** Jumped streams are provably disjoint subsequences, and numpy states that the `PCG64.jumped` method "uses a carefully chosen number of steps to avoid creating these collisions" (B.13 ref 15), which is the low-bit collision A.1a describes. The problem is that `k` is an integer index, and assigning indices to subsystems reintroduces the positional hazard being removed. A persisted index registry to avoid reuse is more fragile than hashing a name.
- **Why not Philox counter-based streams.** `Philox(key=base_seed, counter=name_hash)` is also content addressed and is a legitimate alternative. `SeedSequence` plus `PCG64DXSM` is chosen because the derivation then rests on two published algorithms rather than on a project-specific counter layout, and because `PCG64DXSM` is one line from numpy's default rather than a departure from it: numpy seeds both through the same routine, so the seeded state and increment of A.7 are bit-identical between them, and numpy states that `PCG64DXSM` "will eventually become the new default BitGenerator implementation used by default_rng in future releases" (B.13 ref 15). An earlier draft argued the choice partly on familiarity, that `PCG64` is the construction a reader of numpy code already knows. That argument is weaker now and is not the deciding one, because `PCG64DXSM` is not today's default; what carries the choice is the collision arithmetic of A.1a. Philox is retained as the mechanism for any later vectorised path. No throughput claim is made for either choice here; if throughput becomes the deciding argument it gets a benchmark in the repository, not a sentence.

### A.1a Two collision bounds, both computed

A collision between two streams is a silent correlation bug, so the risk is stated as arithmetic rather than as reassurance. There are two independent bounds and the weaker one governs. Under the bit generator this section chose on 2026-08-09 the weaker one moved, so both are computed here and the move is shown rather than asserted.

**Spawn-key and entropy-pool collision.** The spawn key carries 128 bits, and the `SeedSequence` entropy pool it mixes into carries 128 bits as well. Two distinct stream names that hash to the same key, or two distinct keys that mix to the same pool, produce the same generator. Each is a 128-bit collision, so for `n` names the birthday approximation gives `n^2 / 2^129` in both cases, which at `n = 10^5` is about `1.5e-29`. The name half of that is not left to argument: `test_stream_names_do_not_collide` computes every declared and template-expanded name in the smoke and full scenarios and asserts all spawn keys are distinct. It fails if any two names share a key.

**Bit-generator state collision, and why it stopped governing.** This was the bound that governed while the bit generator was `PCG64`, and it was a documented property of that generator rather than of the derivation above. numpy documents that a pair of `PCG64` streams whose lower 58 state bits agree will, when interleaved, fail the PractRand test battery after a few gigabytes of output, and that the birthday calculation for a 58-bit collision reaches high probability at about `2^29` streams ([numpy reference guide, "Upgrading PCG64 with PCG64DXSM"](https://numpy.org/doc/stable/reference/random/upgrading-pcg64.html), retrieved 2026-08-09, HTTP 200). The same page states that a seeded increment does not add protection against this particular weakness, and that use at thousands of streams is comfortable while use at millions is the point to consider `PCG64DXSM`, `SFC64`, or `Philox`.

The declared ceiling of 750,000 streams sits between numpy's two stated ranges, which is why the choice of bit generator was a decision here and not a default. Both columns below are computed. The left column is the `PCG64` bound, `n^2 / 2^59`, kept because it is the arithmetic that forced the decision. The right column is the 128-bit collision of the spawn key and the entropy pool, `n^2 / 2^129`. That column always applied; under `PCG64` it was hidden behind the larger left one, and under `PCG64DXSM` it is what remains.

| Declared streams | Pairs at 58 shared state bits, `PCG64` | Pairs in the 128-bit pool, governing now | Reading                                   |
| ---------------- | -------------------------------------- | ---------------------------------------- | ----------------------------------------- |
| 1.0e3            | 1.7e-12                                | 1.5e-33                                  | numpy's stated comfortable range          |
| 1.0e5            | 1.7e-8                                 | 1.5e-29                                  | the working size of the current catalog   |
| 7.5e5            | 9.8e-7                                 | 8.3e-28                                  | the ceiling this section sets             |
| 1.0e6            | 1.7e-6                                 | 1.5e-27                                  | numpy's stated "consider PCG64DXSM" range |

**What the switch buys, and what it does not.** numpy publishes no birthday number for `PCG64DXSM`, and none is invented here. What that page does publish is a change of bottleneck: the DXSM output function "adopts a xorshift-multiply construction used in strong integer hashes that has much better avalanche properties than the XSL-RR output function", and with it "collisions are possible, but both streams have to simultaneously be both close in the 128 bit state space and close in the 127-bit increment space, so that would be less likely than the negligible chance of colliding in the 128-bit internal SeedSequence pool". So the documented lower-58-bit weakness is removed, and the residual is bounded above by a 128-bit pool collision, which is the first bound of this section and is computed in the right column. That is the whole of the gain. The switch buys nothing at all against a repeated stream name, a repeated seed, or a draw-order change, which are the failure modes A.2 and A.3 exist for, and it buys no throughput claim, because none was measured. Open question G.14 records that no published `PCG64DXSM` birthday bound was found and names who owns finding one.

`STREAM_COUNT_CEILING = 750000` is a constant in `twinflow_rng.registry`. `test_declared_stream_count_is_under_ceiling` expands every template against the largest shipped facility profile and fails when the total crosses it. The constant keeps its value and loses its former basis: at 750,000 streams the governing bound is now `8.3e-28`, which no longer argues for that number or for any other. It is retained as a declared operating ceiling on catalog size, because a catalog that grows by two orders of magnitude without anyone noticing is a defect whichever bit generator is underneath, and because deleting the check would remove a standing test and record nothing in its place. Crossing it is now a catalog-size review rather than a bit-generator decision, and the failure message says which.

The numbers above bound a statistical artefact, not a seed reuse. Two colliding streams do not produce identical draws; they produce a pair whose interleaving is detectably non-random after gigabytes of output. That is why the ceiling was set by a probability rather than by an assertion of impossibility, and it is why the right column is stated as a bound rather than as a guarantee.

### A.2 Stream naming

Names are dotted, lowercase, and stable. The grammar:

```
<domain>.<subsystem>.<quantity>                     fixed streams
<domain>.<subsystem>.<entity_id>.<quantity>         per-entity streams
provision.<domain>.<entity_id>.<attribute>          entity attributes drawn before the clock starts
fault.<fault_id>.<instance_id>.<quantity>           fault-owned randomness
schedule.faults                                     the one stream that materialises the fault schedule
```

Examples: `twin.receiving.unload_duration`, `twin.amr.AMR-014.task_travel`, `sensor.vibration.CNV-02-VIB-01.noise`, `provision.workforce.W-0231.productivity_effect`, `fault.F-MECH-BEARING.0003.progression`.

Rules:

1. **One stream per (subsystem, quantity) pair.** Never one stream shared by every quantity in a subsystem. Fine granularity means a code change that alters the draw order for one quantity cannot shift any other quantity.
2. **Per-entity streams for anything whose population size varies.** Devices, pallets, lots, orders, AMRs, workers, suppliers, lanes, SKUs. Names key off the stable entity id, so creating entity 501 does not perturb entity 47. Entity ids are themselves deterministic (`AMR-%03d`, `LOT-%s-%06d`) and are assigned from a declared id policy, never from a UUID4.
3. **Per-entity attributes are drawn during provisioning**, before the sim clock starts, from `provision.*` streams. A worker's baseline productivity, a device's manufacturing offset and drift rate, a supplier's true OTIF rate, and a lane's true transit median are all provisioned attributes. This keeps entity identity constant across scenario arms, which is what makes a paired what-if comparison meaningful.
4. **No stream is shared across processes whose interleaving is not deterministic.** SimPy's event queue is deterministic given a total order on events; twinflow fixes the scheduling order as `(sim_time, priority, monotonic_event_counter)` with the counter assigned at scheduling time. No component may break ties on object identity, hash, or memory address. This scheduling order is a different thing from the canonical order of the event log, which D-07 fixes as `(sim_ts, producer_id, seq)` because the log merges several producers and the sequence number is dense only per producer. One process draws in scheduling order; a reader replays in canonical order. Confusing the two produces a reader that appears to work on a single-container run and reorders on a fleet run.
5. **No collection whose iteration order can reach a draw is a `set`.** Applying D-03, this binds every collection that reaches an event, a hash, or a control decision, not only the collection a `for` statement walks. Set iteration order in CPython depends on hash values and insertion history, so a set that is materialised into a list, sorted by a non-total key, or used to build a dict carries the same hazard. Use a sorted sequence, or sort at the iteration site with an explicit total key and say in a comment why the set is the right semantic type. Lint rule `TWF-RNG-002` fails CI on `for ... in <set literal or set()>` inside the sampler and subsystem packages. The lint catches the syntactic case; the standing behavioural check is CI running the determinism scenario twice under different `PYTHONHASHSEED` values and comparing hashes, which catches the cases the lint cannot see.

### A.3 The ordering hazard, stated explicitly

There are two distinct ordering hazards and they need different mitigations.

**Hazard 1: stream allocation order.** Solved by construction. Because a stream's seed is derived from its name and not from a counter, subsystem 40 can be added, removed, or renamed without touching subsystem 1's draws. The stream-append test in section F.4 is the standing proof.

**Hazard 2: draw order within a stream.** Not solved by construction, and this is the one that bites. If a refactor changes how many values a subsystem pulls from its own stream, or the order in which it pulls them, every subsequent draw from that stream shifts and the event log changes. Mitigations:

- Fine-grained streams (rule 1 above) confine the blast radius to the quantity that changed.
- Never draw speculatively. Do not sample a value inside a branch that may be discarded. If a value is needed only sometimes, either draw it unconditionally (accepting the cost) or give the conditional path its own stream.
- Do not draw inside a comprehension or generator whose evaluation order a later refactor might change.
- **When a draw-order change is genuinely required, the stream name gets an explicit version suffix**: `twin.receiving.unload_duration@v2`. The superseded name stays in the registry marked `retired_at: <release>`. Golden files are regenerated in the same commit, and the CHANGELOG compatibility table (C6) records which recorded runs no longer reproduce. This makes an unavoidable break loud, dated, and attributable instead of silent.

### A.4 The stream registry

`packages/twinflow-rng/src/twinflow_rng/registry.py` declares every fixed stream name as a module constant and every per-entity stream as a template. It exports `STREAM_CATALOG_VERSION` (semver).

The registry is the only place allowed to construct generators. The public API is:

```python
rng = streams.get("twin.receiving.unload_duration")           # fixed
rng = streams.get("twin.amr.{amr_id}.task_travel", amr_id=id) # templated
```

`SeedSequence.spawn(` and direct `PCG64DXSM(` construction are forbidden outside `twinflow_rng`; lint rule `TWF-RNG-001` fails CI on either. The rule names every numpy bit generator rather than the chosen one alone, so swapping `PCG64DXSM` for `PCG64`, `Philox`, `SFC64`, or `MT19937` outside the package fails the same way. `numpy.random.seed`, `random.seed`, and module-level `numpy.random.*` calls are forbidden repository-wide (`TWF-RNG-003`), because they touch the legacy global state that nothing here may depend on.

CI test `test_registry_is_append_only` diffs the registry against the previous release tag and fails if any name was removed or altered without a `retired_at` marker and a major version bump.

### A.5 Common random numbers across scenario arms

Because streams are addressed by name, two runs with the same `base_seed` and `replication_index` give the same draws to every stream that exists in both. This is deliberate: it is the variance-reduction technique that raises the statistical power of the LSS engine's before-and-after hypothesis test above an independent-samples comparison of the same size.

The caveat is stated here because a naive implementation gets it wrong. Common random numbers only produce a genuinely paired comparison when the two arms draw the _same number of values_ from each shared stream. Adding a scan portal creates new entities with new stream names and leaves existing streams aligned. Changing an arrival rate changes how many arrivals occur, so pallet number 400 in arm A is not pallet number 400 in arm B, and the pairing is broken even though the stream names match.

The runner so computes a **`crn_integrity` record** for every scenario comparison: for each stream present in both arms, the draw count in each arm. The hypothesis-test assumption checker in the LSS engine consumes it and applies a paired test only when every shared stream's draw counts are identical; otherwise it applies the independent-samples test. The chosen test and the reason are printed in the capability report. Config key: `whatif.crn.enabled` (default `true`), `whatif.crn.require_exact_pairing` (default `true`).

### A.6 What is recorded

Run metadata carries the full RNG state description. See section E.1 for the complete manifest. The RNG-specific fields are `base_seed`, `replication_index`, `rng.mechanism`, `rng.bit_generator`, `rng.stream_catalog_version`, `rng.spawn_key_algorithm`, and `rng.draw_counts_sha256` (a hash over the sorted stream-name-to-draw-count map, which is the cheapest way to detect that a code change altered draw order). `base_seed` and `replication_index` sit in the hashed core; `rng.draw_counts_sha256` sits in the provenance sidecar, because it is computed after the last event and cannot be carried by the first one (D-01).

### A.7 The cross-language derivation, specified byte for byte

One device agent is written in Rust. Applying D-06, that agent derives its stream from the run seed and its device id through the derivation of A.1 rather than through a second mechanism, and the derivation is specified here in terms of named algorithms rather than in terms of whichever library either language happens to call. A conformance test asserts that both implementations produce identical draws for the same stream name and seed.

Three algorithms are named, in this order.

**1. BLAKE2b.** The core compression function is RFC 7693. The personalization parameter is not: RFC 7693 states that salting, personalized hashes, and tree hashing use parameter-block fields outside its scope, and refers to the BLAKE2 specification for them. Both sources are named in B.13 ref 23, and both are needed. Input is the UTF-8 bytes of the stream name. Digest size 16 bytes. Key length 0. Salt absent, which is the 16 zero bytes at parameter-block offsets 32 to 47. Personalization `b"twinflow-rng"` at offsets 48 to 63, 12 bytes zero-padded to 16. The 16-byte digest is read as four little-endian uint32 words `(w0, w1, w2, w3)`, which become the spawn key.

**2. numpy's `SeedSequence` mixing function.** This is a published algorithm with fixed constants, and the constants are part of the contract. They are transcribed from `numpy/random/bit_generator.pyx` at v2.3.0 (retrieved 2026-08-09, HTTP 200):

| Constant            | Value        | Role                                       |
| ------------------- | ------------ | ------------------------------------------ |
| `DEFAULT_POOL_SIZE` | 4            | pool words, so a 128-bit pool              |
| `INIT_A`            | `0x43b0d7e5` | initial multiplier for the mixing pass     |
| `MULT_A`            | `0x931e8875` | multiplier advance inside `hashmix`        |
| `INIT_B`            | `0x8b51f9dd` | initial multiplier for output extraction   |
| `MULT_B`            | `0x58f38ded` | multiplier advance inside `generate_state` |
| `MIX_MULT_L`        | `0xca01f9dd` | left multiplier in `mix`                   |
| `MIX_MULT_R`        | `0x4973f715` | right multiplier in `mix`                  |
| `XSHIFT`            | 16           | the xor-shift distance                     |

All arithmetic is uint32 with wrapping overflow. `h` is one mutable variable shared across every call inside one invocation, and each `hashmix` call advances it before returning, which is why the loops below cannot be reordered.

```
hashmix(v):       v ^= h;  h = h * MULT_A;  v = v * h;  v ^= v >> XSHIFT;  return v   # advances h
mix(x, y):        r = MIX_MULT_L * x - MIX_MULT_R * y;  r ^= r >> XSHIFT;  return r

mix_entropy(pool[4], entropy[8]):
    h = INIT_A
    for i in 0..3:                    pool[i] = hashmix(entropy[i])
    for src in 0..3: for dst in 0..3: if src != dst: pool[dst] = mix(pool[dst], hashmix(pool[src]))
    for src in 4..7: for dst in 0..3:                pool[dst] = mix(pool[dst], hashmix(entropy[src]))

generate_state(n):
    h = INIT_B
    for i in 0..n-1:
        v = pool[i mod 4];  v ^= h;  h = h * MULT_B;  v = v * h;  v ^= v >> XSHIFT;  out[i] = v
```

The entropy array is the four run-entropy words of A.1 followed by the four spawn-key words, in that order, giving the eight words the third loop consumes. A uint64 output word is two uint32 words read little-endian, low word first.

**3. PCG64DXSM, the CM DXSM 128/64 variant.** numpy names this member of the PCG family "PCG CM DXSM 128/64" and states that it "differs from `PCG64` in that it uses the stronger DXSM output function", a 64-bit cheap multiplier in the LCG, and "outputs from the state before advancing it rather than advance-then-output" (`numpy/random/_pcg64.pyx`, the `PCG64DXSM` docstring, v2.3.0, retrieved 2026-08-09, HTTP 200).

Seeding is unchanged from `PCG64`, and that is worth stating plainly, because it fixes how much of an earlier `PCG64` specification survives: all of the seeding half and none of the generation half. `PCG64DXSM.__init__` consumes `generate_state(4, uint64)` exactly as `PCG64.__init__` does, passing words 0 and 1 as the state and words 2 and 3 as the increment into the same `pcg64_set_seed` entry point, which calls `pcg_setseq_128_srandom_r`, the seeding routine shared with the XSL-RR variant. So the four words are read as `(s0, s1, i0, i1)`, `initstate = s0 * 2^64 + s1`, `initseq = i0 * 2^64 + i1`, and the generator is initialised as PCG specifies: state zero, `inc = initseq * 2 + 1`, one step, `state += initstate`, one step, with the step being `state = state * M_XSL + inc` and `M_XSL = 0x2360ed051fc65da44385df649fccf645`. The seeded state and increment a `PCG64DXSM` holds are thus bit-identical to what a `PCG64` seeded from the same `SeedSequence` would hold, and this was checked by reading both back out of numpy rather than by reasoning about the source.

Only generation differs. The output function is DXSM, "double xorshift multiply", it reads the state before the state advances, and the advance uses the 64-bit cheap multiplier `M_CM = 0xda942042e4dd58b5` in place of `M_XSL`. All arithmetic is unsigned and wrapping, at 64 bits inside the output function and at 128 bits in the advance:

```
output(state):     hi = state >> 64                             # uint64
                   lo = (state mod 2^64) bitwise_or 1           # uint64, forced odd
                   hi = hi xor (hi >> 32)
                   hi = (hi * 0xda942042e4dd58b5) mod 2^64
                   hi = hi xor (hi >> 48)
                   hi = (hi * lo) mod 2^64
                   return hi

advance(state):    state = (state * 0xda942042e4dd58b5 + inc) mod 2^128

next_uint64():     out = output(state); advance(state); return out
```

Three details in that block are the ones an implementer gets wrong. The output precedes the advance, where XSL-RR advances first. The cheap multiplier is a 64-bit constant widened to 128 in the advance, not a 128-bit constant. The forced odd bit on the low word is load-bearing, because multiplication modulo `2^64` by an even value is not a bijection, so an even `lo` would collapse distinct states onto one output. These are transcribed from `pcg_output_cm_128_64`, `pcg_cm_step_r`, and `pcg_cm_random_r` in `numpy/random/src/pcg64/pcg64.h`, with `pcg_advance_lcg_128` in `pcg64.c` for the jump path, at v2.3.0 (retrieved 2026-08-09, HTTP 200). The same header also carries `pcg_cm_srandom_r`, which seeds with the cheap multiplier. numpy does not call it, and a second implementation that does will produce a different state from the same seed.

**The Rust binding.** The crate is `rand_pcg`, and the type is `Lcg128CmDxsm64`, exported under the alias `Pcg64Dxsm`. Its documentation states that it "corresponds to `pcg_engines::cm_setseq_dxsm_128_64` from pcg_cpp and `PCG64DXSM` from NumPy" ([rand_pcg 0.10.2 documentation](https://docs.rs/rand_pcg/0.10.2/rand_pcg/struct.Lcg128CmDxsm64.html), retrieved 2026-08-09, HTTP 200). Binding the type is not enough, and this is the trap: `Lcg128CmDxsm64::new(state, stream)` does not reproduce numpy's seeded state, because it adds the increment once and takes a single step with the cheap multiplier, where numpy takes two steps with `M_XSL` starting from zero. The agent computes the seeded state with the routine above and then calls `Lcg128CmDxsm64::from_state(seeded_state, initseq)`, which sets `increment = (initseq << 1) | 1` and leaves the state alone. `from_state` is why the crate floor is `rand_pcg` 0.10: version 0.9.0 exposes only `new` and `advance` on this type, so it cannot be handed a pre-seeded state and would need a vendored copy instead. The 0.10 series is MIT or Apache-2.0, which the inbound dependency license policy in `ARCHITECTURE.md` decision D15 accepts.

**The conformance corpus.** `tests/fixtures/rng_kat.json` holds known-answer vectors: for each of 64 stream names spanning every grammar form of A.2, at three base seeds and two replication indexes, the first 16 raw uint64 outputs and the first 16 doubles. `test_rng_known_answers` in Python and `rng_known_answers` in Rust read the same file and compare. A change to any of the three algorithms fails both suites in the same commit. The corpus is generated by a script that prints the numpy result, so the fixture records what numpy does rather than what this document says it does, and a disagreement between the two is itself a finding.

**What the agent draws.** The Rust agent owns the streams named `device.agent.<device_id>.<quantity>`, which is the per-entity form of the A.2 grammar: publish jitter, backoff jitter on reconnect, store-and-forward eviction choice, and sample-interval jitter for locally generated readings. It never draws a physical quantity; physical state arrives from the twin. This keeps the agent's contribution to the tape small enough that the conformance corpus covers it exhaustively.

### A.8 Solvers and learned models

Applying D-04, a component whose output steers the simulation is bounded deterministically or it does not steer the simulation.

| Component                           | How it stays deterministic                                                                                        |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Constraint solver (rostering, yard) | Deterministic budget rather than wall-clock seconds, a branch cap, one worker, and a fixed solver seed            |
| Learned AMR dispatch (E11)          | Pinned model artefact hash, fixed seed, fixed thread count, deterministic kernels, called through `Inference`     |
| Learned detectors and forecasters   | Same contract, and in simulation mode `Inference` binds a recorded-response adapter                               |
| Surrogate model (E28)               | Advisory only: it ranks candidate scenarios and the full simulation confirms the winner, so it never steers a run |

Where determinism cannot be reached, the component becomes an advisory output recorded in the provenance sidecar, and the tape records the decision it produced rather than recomputing it on replay. `test_inference_port_is_bound_to_recorded_adapter_in_simulation_mode` fails when a simulation-mode run constructs a live inference client. Model training is a separate matter and is covered in E.4.

## B. The common-cause distribution catalog

### B.1 Where it lives and how it is parameterised

The catalog lives in `config/distributions.yaml`, validated at load against `schemas/distributions.schema.json`, and carries its own `catalog_version` (semver) recorded in every run manifest. `facility.yaml` references it by path and pins the version. Sensor signal models live in `config/sensors/*.yaml` (the sensor catalog, one entry per type) and follow the same family grammar.

Config keys below are dotted paths into `distributions.yaml` rooted at `variability.`. A leading `sensors.` denotes the sensor catalog instead.

Every family is parameterised in terms a practitioner can estimate, not in terms of the raw canonical parameters. The sampler converts. Conversions are unit tested against closed forms.

| --------------------------------------------------- | --------------------------------------------------------------------- | ---------------- |

The family list is closed. `test_every_catalog_family_is_declared` reads `config/distributions.yaml` and `catalog/sensors/*.yaml` and fails on a family name absent from the table above, which is what stops a catalog entry from introducing an undocumented sampler.

Applying D-10, the sampler needs numpy and nothing else. The conversions below are closed forms, so no fitting library is imported at run time. The goodness-of-fit suite of F.3 needs `scipy` for the Anderson-Darling and chi-square distributions and declares it under the `test` extra.

Three conventions that matter downstream:

- **`hierarchical` is not decoration.** The two-level structure is what gives the Gage R and R study a ground truth: the entity-level effect is the true operator or gauge variance component, and the within-level effect is the true repeatability component. The MSA test suite compares the engine's estimated variance components against the provisioned values.
- **Deterministic parts stay deterministic.** Conveyor transport time is `length / speed`, ASRS crane time is the Chebyshev kinematic time, and putaway travel distance is fixed by the slotting assignment. Only the multiplier or the jitter is drawn. The catalog rows say so, and this keeps the twin's mechanistic core inspectable.
- **`normal` appears on readings, not on quantities.** A physical quantity with a floor never takes a `normal`, because the family's support is the whole real line and the quantity's is not. A measured reading does take one, because additive electrical noise on a measurement is unbounded even when the measured quantity is bounded. Section B.10 states the same rule from the sensor side, and `test_no_normal_family_on_a_bounded_physical_quantity` fails when a `variability.*` key outside the sensor catalog names `normal`.

### B.10 Sensors: the generic signal model

Every sensor type in `config/sensors/*.yaml` declares its reading as the same additive composition. Adding sensor type 300 is a catalog entry that fills in these slots, not new code.

```
reading(t) = quantise(
                 baseline(twin_state, t)          # physics-informed, deterministic given state
               + unit_offset                      # provisioned once per device
               + drift(t)                         # slow, signed
               + noise(t)                         # fast
               + fault_overlay(t),                # zero unless a fault instance is active
                 resolution)
```

| Component              | Family                                                                   | Parameters (catalog keys)                       | Support       | Justification                                                                                                                            |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `baseline`             | deterministic function of twin state, optionally with a first-order lag  | `sensors.<type>.signal.baseline.*`, `lag_tau_s` | physical      | The sensor measures something the twin already knows; thermal mass and similar dynamics are modelled as a lag, not as noise              |
| `unit_offset`          | `normal(0, sigma_offset)` provisioned once per device                    | `sensors.<type>.signal.unit_offset_sigma`       | `R`           | Unit-to-unit variation is the gauge bias component in MSA, and it must be persistent per device to be measurable                         |
| `drift`                | `wiener(drift_per_day, sigma_per_sqrt_day)`, drift sign drawn per device | `sensors.<type>.signal.drift.*`                 | `R`           | Real drift has both a deterministic slope and a random-walk component; a pure ramp would be too easy to detect                           |
| `noise` (white)        | `normal(0, sigma_noise)`                                                 | `sensors.<type>.signal.noise.sigma`             | `R`           | Additive electrical noise on a _measurement_ is unbounded even when the measured quantity is bounded, and that is correct                |
| `noise` (coloured)     | `ar1(phi, sigma)` approximating 1/f                                      | `sensors.<type>.signal.noise.phi`               | `R`           | Vibration, strain, and current noise are not white; an AR(1) captures the autocorrelation that would otherwise make control limits wrong |
| `quantise`             | deterministic rounding to ADC resolution                                 | `sensors.<type>.signal.resolution`              | discrete grid | Resolution sets the number of distinct categories in MSA and must be modelled to make the discrimination ratio meaningful                |
| Sample interval jitter | `gamma(mean=nominal, shape=60)`                                          | `sensors.<type>.timing.interval_jitter`         | `(0,inf)`     | Real devices do not sample on an exact grid                                                                                              |
| Clock offset           | `wiener` plus a per-device `skew_ppm ~ normal(0, 12)`                    | `sensors.<type>.timing.clock`                   | `R`           | Baseline clock behaviour; F-DEV-CLOCKDRIFT is an extreme value of the same mechanism                                                     |
| Per-sample dropout     | `bernoulli(p)` with `p ~ beta_scaled(0,1,0.0008,4000)` per device        | `sensors.<type>.reliability.dropout`            | `{0,1}`       | Baseline lossiness, distinct from the injected outage faults                                                                             |

**No clamping rule, restated for sensors.** A reading is never clipped to the physical range of the measured quantity. A thermocouple that reads -270 C after a calibration loss is emitted as -270 C, because that reading is exactly the fault signature a detector must catch. The validity range declared in `sensors.<type>.validity` is consumed by the metrics layer, which excludes out-of-range samples from KPI computation and raises a data-quality finding, while detectors read the raw stream. See open question G.9.

## C. The fault catalog: special-cause injection

### C.1 How faults are injected

Two injection layers, kept strictly apart.

- **Physical layer.** The fault changes the twin's state or parameters: bearing wear multiplies the vibration baseline, a jam seizes a resource, a supplier outage stops ASN generation. Injected through a `FaultOverlay` object the twin consults when it evaluates a parameter.
- **Telemetry layer.** The fault changes the message stream between the device agent and the broker: drop, duplicate, delay, reorder, corrupt, stall, or resend. Injected in the device agent's publish path and in the broker adapter.

Applying D-08, the telemetry layer injects at the `Network` port, which is the MQTT-shaped one, because every fault in C.4 is defined in terms of retained messages, quality of service, last will, or wildcard subscription. `EventBus`, which carries analytics fan-out and has no retain and no will, takes exactly two faults: `F-SEC-RANSOM` when the historian is the target, and `F-IT-CHANGE` when the change lands on the information layer rather than on the broker. A fault declaration names its port, and `test_fault_declares_a_port_that_supports_its_primitives` fails when an MQTT primitive is requested on `EventBus`.

Applying D-09, the primitives themselves are the kernel's. `docs/design/foundations.md` owns `FaultKind`, `Fault`, and `FaultSchedule`, and this section owns the catalog that composes them into named, labelled conditions. The kernel's `Fault.rng_stream` defaults to `kernel.net.faults`, which is the stream used when the kernel is exercised standalone in its own resilience tests. A catalog instance always overrides that default with its own `fault.<fault_id>.<instance_id>.<quantity>` name, so two instances of one fault class never share draws and R6 holds. `test_catalog_instance_never_uses_the_kernel_default_stream` fails on any materialised instance that leaves the default in place.

The separation is enforced, not merely documented. A stuck sensor does not stop the conveyor. Test `test_telemetry_faults_are_physically_inert` runs a scenario containing only telemetry-layer faults and asserts the physical KPI series is byte-identical to the fault-free run at the same seed.

That test only passes because of **R6**: faults transform samples, they never consume subsystem draws. A fault multiplies a parameter, replaces a returned value, or gates a publish. Any randomness a fault needs (jitter on a reconnect, which message a buffer drops, the exact progression of a degradation) comes from `fault.<fault_id>.<instance_id>.<quantity>`. Test `test_fault_activation_does_not_change_draw_counts` asserts the per-stream draw-count vector is identical with and without each fault.

### C.2 The fault schedule

Two modes, both producing the same artefact.

- **Explicit.** `config/faults/<scenario>.yaml` lists instances with fixed onset times and parameters. This is what the labelled evaluation scenarios use, so their labels never move.
- **Stochastic.** Fault classes declare arrival rates. At run start, before the sim clock advances, the `schedule.faults` stream samples the instances and **materialises them into an explicit schedule**, which is written to `runs/<run_id>/fault_schedule.json` and hashed into the manifest.

Materialising up front matters for two reasons. The fault stream never interleaves with subsystem streams, so scheduling cannot perturb the physics. And a counterfactual replay can carry the identical schedule forward verbatim while changing the config, which is what makes the counterfactual a controlled comparison instead of a new experiment.

Faults are not scheduled inside the LSS engine's Phase I baseline window unless the scenario explicitly opts in. `SCN-CONTAM` opts in on purpose, because a baseline computed on a contaminated window is a real and instructive SPC failure.

### C.6 Scoring detectors against truth

Matching rule. A detector alarm at sim time `t` on stream `s` is a **true positive** if an unmatched fault instance exists whose `affected_streams` contains `s` and for which `t_effect_start <= t <= t_clear + scoring.grace_s`. Each alarm matches at most one instance, resolved earliest-instance-first. Alarms outside every window are **false positives**. Instances with no matched alarm are **false negatives**.

Reported metrics, per fault class and overall:

- Precision, recall, F1.
- Mean time to detect, computed from `t_effect_start`, and a second figure computed from `detectable_from` so severities are comparable.
- **False alarms per 1,000 operating hours**, reported against the chart's in-control average run length rather than against zero. This is the metric that makes the document's central point measurable. Three-sigma limits on a normal process leave 0.0027 of the distribution outside, both tails together (B.13 ref 2), so a single-rule individuals chart has an in-control average run length of `1 / 0.0027 = 370.4` samples. A chart applied to an untransformed lognormal cycle time produces far more than that, and the excess is a mis-specified chart rather than a noisy process. The combined Western Electric rule set has its own exact in-control run length, near 91.75, from Champ and Woodall (B.13 ref 17), and a chart running that rule set is compared against 91.75 rather than against 370.4.
- Detections before `detectable_from`, whose expected count is zero. A non-zero count is investigated as a label-leakage or windowing bug, not celebrated.

Applying D-11, the false-alarm comparison is a gate and carries all four of a gate's parts. Its reference is external and named above. Its tolerance is set from the Monte Carlo noise floor of the measurement rather than chosen: the count of false alarms in a fault-free window of `n` samples is binomial, so the noise floor is the Clopper-Pearson interval around the count (B.13 ref 19). The gate declares its own sample size rather than inheriting whatever `SCN-CLEAN` happens to produce, and F.7 states both the size and the resulting interval. Its falsifier is stated: a detector whose measured in-control run length on `SCN-CLEAN` falls outside the interval around its chart's published value has either a wrong control limit or a wrong distributional assumption, and the report names which by re-running the same series under `lss.chart_selection: declared`. VG-VAR-01 in F.7 records the gate.

Because ground truth exists, every one of these is measured rather than asserted. That is the differentiator stated plainly in section D.

## D. Common cause versus special cause

### D.1 How a reader tells them apart

The test is mechanical, and that is the point.

- If the variation's source is an entry in `config/distributions.yaml` or a sensor catalog signal model, it is **common cause**. It is the process behaving as designed, including its tails.
- If the variation's source is an instance in the run's materialised fault schedule and appears in `ground_truth/faults.jsonl`, it is **special cause**. It has an identifiable assignable origin, a start, and usually an end.

There is no third category and no ambiguity about which file to look in.

### D.2 Why both exist

Without heavy, honest common-cause variation, every detector scores near-perfectly and the repo proves nothing. A control chart on a low-variance, thin-tailed process is a trivial exercise, and any anomaly detector clears it. Removing tails to make results look good would be exactly the dishonesty the repo is built to avoid, which is why **R3** forbids truncation and CI lints for clamps.

Without labelled special causes, no detector can be scored at all. Real deployments live in this state permanently: an alarm fires, someone investigates, and the truth is whatever the investigation concluded. Precision and recall are unavailable because there is no answer key.

The boundary between the two is the thing the statistical engine is being tested on. The engine's entire job is to look at a stream that contains both and say which is which, on time, without flooding the operator.

### D.3 The two declared boundary cases

Honesty requires naming where the boundary is genuinely fuzzy. There are exactly two places, and both are declared rather than hidden.

**Rate-elevated event classes.** Jams, mis-sorts, absences, and device dropouts all occur at a baseline rate in the distribution catalog _and_ appear in the fault catalog as rate multipliers. A jam at the baseline rate is common cause. A jam inside an F-CONV-JAM window is special cause. Individual events are not labelled; the _window_ is. Scoring so treats the window as the unit of truth, and a detector that flags a single baseline jam outside any window is counted as a false positive, correctly.

**Common-cause tail draws.** A lognormal unload duration can produce a value that looks exactly like a fault. It is labelled common cause because that is what it is. A detector that flags it is scored as a false positive. The document states plainly that a fraction of those false positives are the chart behaving correctly at its nominal false alarm rate, which is why C.6 requires false alarms to be reported against the theoretical in-control average run length rather than against zero.

This is also why chart selection matters, and why the engine gets two modes:

- `lss.chart_selection: empirical` (default). The engine infers the distributional shape from a fault-free warm-up window and chooses the chart and any transformation from that. This is the honest number and it is the one the README publishes.
- `lss.chart_selection: declared`. The engine reads the family directly from `distributions.yaml`. This is an upper bound on achievable performance, useful for separating "the chart was wrong" from "the signal was not there".

Both are reported in the capability report. Publishing only the second would be cheating, and publishing only the first would hide how much of the gap is chart mis-specification.

### D.4 The differentiator, stated plainly

Because the injection is known, twinflow measures detector precision, recall, and mean time to detect against truth. No real deployment can do this. A live plant can tell you an alarm fired and, eventually, what an engineer concluded; it cannot tell you how many real faults the detector silently missed, because the missed ones leave no record. That asymmetry is why published anomaly-detection performance in industry is mostly precision-shaped and almost never recall-shaped.

The same property applies across four layers, and each is scored the same way:

- Anomaly detection is scored against the fault windows.
- Predictive maintenance is scored against the true remaining-useful-life series.
- Process mining conformance is scored against the twin's designed reference model, which is a known ground-truth process. Applying D-14, the miner doing that scoring is `twinflow-procmine`, written in this repository under Apache-2.0, because PM4Py and `pm4pyminimal` are AGPL-3.0 and section 13 of that license triggers on network interaction, which this project has in three places. PM4Py stays available as a development-only oracle that CI compares against without distributing or serving it, which is what gives the conformance numbers an external reference under D-11.
- Causal discovery is scored against the declared causal graph and, in the weather case, against a known confounder.

The repo's shipping rule follows directly: a learned model ships only if it beats the statistical baseline on these labelled scenarios, and both numbers are published. This catalog is that labelled test set.

One honest limitation is stated in the same breath, in the README and here: synthetic labels are only as good as the generator that produced them. The measured numbers describe performance on twinflow's declared distributions and declared faults. They are not a claim about performance on any real operation, and the catalog is published in full so a reader can judge whether the assumptions are reasonable.

The split has four consequences, and each one is a place an implementer would otherwise put a field on the wrong side.

1. **Git provenance is not part of run identity.** `run_id` addresses the inputs of an experiment: seed, replication, config, schema snapshot, fault schedule, scenario, mode. A code change that leaves those inputs alone produces the same `run_id` and a possibly different log, which is exactly the condition `twinflow replay` is built to detect and report against the CHANGELOG compatibility table. Folding the git sha into the id would hide that condition by making every build's run a different experiment.
2. **The draw-count hash is sidecar.** It is computed after the last draw, so the first event cannot carry it. It is compared between two runs of the same `run_id`, and a difference names a draw-order change rather than a value change.
3. **`stream_count_declared` is sidecar and is checked against `STREAM_COUNT_CEILING`** of A.1a on every run, so the collision bound is monitored on real configurations rather than assumed from the registry.
4. **The carve-out is tested, not trusted.** `test_run_started_carries_no_wall_clock_or_platform_field` walks the `run_started` payload schema and fails on any property whose name or type is a wall-clock instant, a host name, a package version, or a platform field. A field added later to the sidecar cannot drift into the hash without that test failing.

`resolved_config.yaml` is the config after defaults, includes, profile overlays, and environment overrides have been applied. It is the artefact that determines behaviour, so it is the one that is hashed and stored, not the source files alone. `invocation_id` keeps two deliberate repeats distinguishable and lives in the sidecar, because a value that is unique per invocation would break byte identity if it entered the log.

### E.2 Replay

```
twinflow replay --run <run_id>
```

Reads the manifest, restores `resolved_config.yaml`, restores the materialised fault schedule, re-runs, and asserts every hash in `outputs` matches. If `code_version.git_sha` differs from the current checkout, the CLI prints the difference and consults the compatibility table in CHANGELOG (per C6) to say whether the release is expected to reproduce that run. It does not silently proceed.

### E.3 Counterfactual replay

```
twinflow replay --run <run_id> --set stations.putaway.scan_portals=2 --label "second portal at dock 3"
```

Rules:

1. `base_seed` and `replication_index` are carried over unchanged.
2. The **materialised** fault schedule is carried over verbatim. It is not resampled. The same faults hit at the same times, so the arms differ only by the config change.
3. The config change is applied to the resolved config, producing a new resolved config, a new hash, and a new `run_id`. The manifest sets `derived_from` to the parent and stores the config diff.
4. The runner emits `crn_integrity.json`: the per-stream draw counts for both arms and the set of streams present in only one arm.
5. The LSS engine reads `crn_integrity.json` and applies a paired test only when every shared stream's draw counts match, otherwise an independent-samples test, and prints which it used and why.

Point 5 is the part a naive implementation gets wrong. Common random numbers give partial variance reduction whenever the change alters how many draws a stream produces, and treating a partially-aligned comparison as paired inflates the apparent significance of the improvement. The engine refuses to do that.

### E.4 Determinism hazards that are actively managed

- **Global RNG state.** Forbidden repository-wide by lint `TWF-RNG-003`.
- **Set iteration.** Forbidden in drawing paths by `TWF-RNG-002`, and the behavioural backstop is CI running the determinism scenario twice under different `PYTHONHASHSEED` values (D-03).
- **Dict ordering.** Python dicts are insertion-ordered, which is enough, but insertion order must not depend on filesystem enumeration order. All directory scans are sorted, and any dict built from a set is sorted before use.
- **Event-queue ties.** Scheduling order fixed as `(sim_time, priority, monotonic_event_counter)`. The canonical order of the log is the separate `(sim_ts, producer_id, seq)` of D-07, and A.2 rule 4 states why the two are not the same thing.
- **Wall clock.** Applying D-02, a wall clock may be read in exactly four places: the provenance sidecar writer, the paced-clock pacer, the observability exporter, and operator-facing log lines. In all four the value never enters an event payload, never enters the hashed tape, and never steers control flow. The pacer is the apparent exception and is not one: pacing changes when an event is emitted in wall time, never which event or in what order, and `test_pacing_does_not_change_the_tape` compares a paced run against an unpaced one. Everything else reads the injected `Clock`.
- **Hostname, PID, UUID4.** Never enter the event log. Lint `TWF-DET-001` fails on `uuid4`, `time.time`, `datetime.now`, `socket.gethostname`, and `os.getpid` in the twin, sensor, and LSS packages, and `scripts/checks/nondeterminism-gate.sh` enforces the same outside the kernel package.
- **Threading and BLAS.** Runs marked deterministic set `OMP_NUM_THREADS=1` and equivalents, recorded in the manifest.
- **Float serialisation.** Floats are written with shortest round-trip repr, so a value that is bit-identical serialises identically.
- **Transcendental functions.** `log`, `exp`, and `erfinv` are SIMD-dispatched in numpy and can differ across CPU microarchitectures and library builds. The byte-identity guarantee is so scoped to the platform recorded in the provenance sidecar. Across platforms, CI asserts the weaker contract in E.5. See open question G.1.
- **Machine learning training.** Not covered by the byte-identity guarantee. Framework nondeterminism is out of scope here; model artefacts are versioned and hashed by the MLOps layer instead, and the guarantee in this section covers the simulation event log, the findings stream, and the ground-truth files. Inference is a different matter and is covered by A.8, because inference inside the loop steers the tape while training does not.

**The cross-platform check, stated the way D-05 requires.** It does not assert a tolerance chosen in advance. It runs `SCN-CLEAN` in every matrix cell, then compares against the reference cell in two steps.

1. **Business events are identical.** The ordered tuple of event type, entity id, and canonical order rank matches exactly. Any difference here is a defect, never a rounding artefact, because the discrete decisions the twin makes are comparisons against thresholds and a one-unit-in-last-place difference cannot flip one without also changing the tape's shape.
2. **Continuous fields agree inside a measured tolerance.** The gate computes the maximum relative divergence across every continuous field and reports it. The tolerance is `divergence_tolerance`, a config value seeded from the maximum observed over the previous 30 nightly runs plus a factor of two, and it is committed to the repository as a number with the date it was measured. When a run exceeds it, the gate names the two candidate explanations in its output: the tolerance was measured on too few platforms, or a real defect was introduced. It does not pick one.

The reason for measuring rather than asserting is stated once, in E.4: `log`, `exp`, and `erfinv` are SIMD-dispatched in numpy and can differ in the last bits across CPU microarchitectures and library builds, and inverse-CDF sampling puts those functions on the path of nearly every draw. A number chosen in advance for that divergence would be a guess wearing a gate's clothes.

## F. Testing

### F.1 Unit tests

- **Parameterisation conversions.** Every family's practitioner parameters convert to canonical parameters correctly: `lognormal(median, sigma_log)` to `(mu, sigma)`, `gamma(mean, shape)` to `(shape, scale)`, `beta_scaled(lo, hi, mean, conc)` to `(alpha, beta)` with the affine map, `negbin(mean, disp)` to `(n, p)`. Tested against closed forms with exact expected values.
- **Moment checks at a fixed seed.** Sample mean and variance fall inside a Monte Carlo confidence interval computed from the analytic moments. Uses a dedicated `test.*` stream so it cannot perturb simulation streams.
- **Config validation.** Out-of-range and mistyped parameters raise line-numbered errors with suggestions, per C5. A `sigma_log` of zero, a `beta_scaled` with `lo >= hi`, and a `negbin` with `disp <= 0` each have a named test.
- **Family registry integrity.** The family named in `distributions.yaml` resolves to the sampler class actually constructed. A typo cannot silently select a different family.
- **Fault parameter validation.** Every fault's parameter schema rejects a negative duration, an unknown target id, and an onset window outside the run horizon.

### F.2 Property-based invariants

Hypothesis-class generators over the schema-declared parameter ranges. Named invariants, each a separate test:

1. `durations_strictly_positive` - every sampled duration is `> 0`, strictly, for every valid parameter set. Float underflow to `0.0` counts as a failure; if a schema-legal parameter set can underflow, the schema range is wrong and gets tightened, not the sample clamped.
2. `bounded_ratios_within_bounds` - every `beta_scaled` draw lies in `[lo, hi]`. The closed interval is intentional: a beta can return exactly `0.0` or `1.0` in float64, and consumers must tolerate it rather than the sampler hiding it.
3. `counts_are_nonnegative_integers` - every count family returns a non-negative integer of the declared dtype, and shifted families respect their declared minimum.
4. `material_conservation` - per station and per interval, `units_in == units_out + wip_delta + scrap + shrink`, as exact integer accounting with no tolerance.
5. `monotone_clock` - sim time is non-decreasing along every entity's event sequence, and the global log is non-decreasing under the declared tie-break key. Carve-out: device-reported _source_ timestamps may go backwards under F-DEV-CLOCKDRIFT and F-NET-REORDER. The invariant binds sim time and historian ingest order, never device-reported time, and the test asserts the carve-out is exercised.
6. `genealogy_closure` - every lot, pallet, and carton has a parent chain terminating at a receipt or a production input; the genealogy graph is acyclic; every consumed unit appears in exactly one child; no orphans.
7. `ledger_balance` - debits equal credits per posting and per period; inventory value change reconciles to receipts minus issues plus revaluation; cash movements reconcile to the statement.
8. `soc_and_soh_bounds` - battery state of charge stays in `[0,1]` and state of health is monotone non-increasing, for every AMR over every run.
9. `resource_capacity_respected` - no resource serves more than its declared capacity; no queue length is negative.
10. `no_negative_inventory` - on-hand is `>= 0` at all times unless `inventory.allow_negative` is explicitly set.
11. `fault_window_wellformed` - every ground-truth instance satisfies `t_inject <= t_effect_start <= t_effect_end <= t_clear`, and all lie inside the run horizon.
12. `telemetry_faults_physically_inert` - a run with only telemetry-layer faults produces a byte-identical physical KPI series to the fault-free run at the same seed.
13. `draw_counts_invariant_under_faults` - the per-stream draw-count vector is identical with and without every fault, individually and in combination. This is R6 made testable.
14. `causal_graph_is_dag` - the declared causal graph is acyclic and every fault's `causal_edges` reference declared nodes.
15. `sensor_readings_are_not_clamped` - driven to a synthetic extreme state, a sensor emits a reading outside the declared physical validity range. A pass proves no hidden clamp exists; a failure means someone added one.

### F.3 Goodness-of-fit

For every entry in the catalog, draw `N` values from the implemented sampler and test against the declared CDF.

- **Continuous families: Anderson-Darling.** Chosen over Kolmogorov-Smirnov deliberately. The NIST/SEMATECH e-Handbook states that Anderson-Darling "gives more weight to the tails than does the K-S test" (B.13 ref 1), which is exactly where R3 makes correctness matter most, and that its critical values depend on the distribution being tested, which is why each family carries its own (B.13 ref 21).
- **Discrete families: chi-square** with tail pooling so no expected cell falls below 5, the convention Cochran (1954) states (B.13 ref 20). The current edition of the e-Handbook no longer prints that threshold in its chi-square page, so the rule is attributed to Cochran rather than to NIST.
- **Tail-specific check, run for every family.** Compare empirical exceedance probabilities at the 0.99, 0.999, and 0.9999 quantiles against the analytic values inside an exact binomial confidence interval, computed by the Clopper-Pearson method (B.13 ref 19). This is the check that catches an accidental clamp or cap, which a centre-weighted test would pass without complaint. At `N = 500,000` the expected count above the 0.9999 quantile is 50, so the interval is wide enough to be honest and narrow enough to catch a cap that removes the tail entirely.
- **Hierarchical families** are tested by variance-component recovery: fit a random-effects model to a large sample and confirm the recovered entity and within components match the provisioned values within a confidence interval. This doubles as the ground-truth fixture for the Gage R&R validation.
- **Process families** (`ou`, `ar1`, `wiener`, `semi_markov`, `nhpp`) are tested on their defining statistics: the OU stationary distribution and autocorrelation at declared lags, the AR(1) coefficient, the Wiener increment variance scaling with the square root of elapsed time, semi-Markov holding-time distributions per state, and the NHPP intensity recovered by binned counts against the declared profile.

**Multiple-testing control.** With roughly 170 catalog entries, testing at alpha = 0.01 would produce around 1.7 spurious failures per CI run and a permanently flaky suite. Two mitigations, both required:

1. The GoF suite runs from a fixed dedicated seed distinct from any run seed, so a failure is deterministic and reproducible rather than intermittent.
2. Benjamini-Hochberg false-discovery-rate control is applied across the whole suite at `q = 0.05` (B.13 ref 18). The suite fails if the adjusted rejection set is non-empty, and the report names which entries were rejected with their raw and adjusted p-values.

**Runtime budget.** PR CI runs `N = 20,000` per entry with correspondingly wider intervals, budgeted at 300 seconds. Nightly runs `N = 500,000`, budgeted at 25 minutes. Both are in the same test module, parameterised by an environment variable recorded in the report. F.7 holds the arithmetic that makes those two numbers checkable rather than aspirational.

### F.4 The stream-addition test

Two forms, both required, because they catch different mistakes.

**Form 1, digest fixture.** `tests/fixtures/stream_digests_v<catalog_version>.json` maps every declared stream name to the SHA-256 of its first 32 draws at a pinned base seed. The test re-derives every stream and compares. It then registers a synthetic new stream `test.synthetic.newstream_<uuid-free-counter>`, draws from it, re-derives every original stream, and asserts every digest is still unchanged.

**Form 2, end-to-end.** Run `SCN-CLEAN` and record `event_log_sha256`. Register a no-op subsystem that claims a new stream and draws 10,000 values from it during the run. Re-run at the same seed. Assert `event_log_sha256` is unchanged.

Form 2 is the one that catches an accidental positional `spawn()` slipping into the codebase, because form 1 would still pass if the fixture were regenerated carelessly. A companion static test asserts the string `SeedSequence(` and `.spawn(` appear nowhere outside `twinflow_rng`.

### F.5 Scoring-harness tests

The detector scoring code is itself tested against hand-constructed fixtures, because a scoring bug would silently invalidate every published number.

- Alarm exactly at `t_effect_start` counts as a true positive.
- Alarm exactly at `t_clear + grace_s` counts as a true positive; one microsecond later does not.
- Two alarms inside one window produce one true positive and one false positive.
- Two overlapping instances on the same stream and one alarm produce one true positive and one false negative under the greedy earliest-first rule.
- An instance with no `affected_streams` entry matching any monitored stream is excluded from recall with an explicit reason, not silently counted as missed.
- False alarms per 1,000 hours is computed on operating hours, not sample count.

### F.6 Golden files

Per C4, seeded end-to-end scenarios compare against golden files for the capability report, the value stream map, the financial statements, and `ground_truth/faults.jsonl`. Golden regeneration requires an explicit `just regen-goldens` invocation, produces a diff summary in the PR, and is never automatic.

### F.7 Validation gates and runtime budgets

#### F.7.1 What this section may call a gate

Applying D-11, a gate here satisfies five conditions, and a check that misses any one of them is a test rather than a gate. It names a specific external published reference with an edition and a locator. Its tolerance is never tighter than the precision of the published value it checks. A gate over a stochastic quantity states a measured noise floor and sets its tolerance above it. It states the result that would falsify it. A statistic with no valid external reference is recorded in section G and never as a passing gate.

The distinction has teeth in one place a reader will look for it. The variance-component recovery check in F.3 compares the engine's estimates against twinflow's own provisioned values. That is a strong test and it is not a gate, because the reference is this repository. It stays in F.3 under its own name, and the Gage R and R claim it supports is gated in `docs/design/lss-engine.md` against a published measurement-system example instead.

Gates register in the same `validation/valgates.yaml` the LSS engine defines, under the `VG-VAR` prefix, and carry the same `status` field. `just phase-gate <phase>` exits non-zero when any gate assigned to that phase is not `PASSING`. A gate whose reference text has not been retrieved ships as `PENDING` with the reason recorded, which keeps the claim out of the capability report until the evidence exists.

#### F.7.2 Runtime budgets

Applying D-13, every tier carries a budget and the arithmetic is tested rather than hoped for.

| Tier                              | Budget          | What dominates it                                                                   |
| --------------------------------- | --------------- | ----------------------------------------------------------------------------------- |
| F.1 unit                          | 60 s            | Closed-form conversions and config validation, all cheap                            |
| F.2 property                      | 180 s           | Hypothesis in its derandomized profile, `max_examples` tuned per invariant          |
| F.3 goodness of fit, pull request | 300 s           | 170 entries at `N = 20,000`, dominated by the test statistics rather than the draws |
| F.3 goodness of fit, nightly      | 25 min per cell | 170 entries at `N = 500,000`                                                        |
| F.4 stream addition               | 120 s           | Form 2 runs `SCN-CLEAN` twice with a synthetic stream registered                    |
| F.5 scoring harness               | 30 s            | Hand-constructed fixtures only                                                      |
| F.6 golden files                  | 600 s           | The seeded end-to-end scenarios                                                     |
| F.7 validation gates              | 300 s           | The Monte Carlo gates VG-VAR-01, VG-VAR-02, and VG-VAR-05                           |

The largest single job is 600 s, which is at or below the pull-request job cap the repository craft section states, and the nightly cell is 25 minutes against a 35 minute cap.

`test_tier_budgets_fit_the_job_budget` asserts the arithmetic from measurements rather than from assumed constants. It reads the per-entry timing that the previous nightly run recorded, multiplies by the current catalog entry count, and fails when the product exceeds the tier budget. A catalog that grows from 170 entries to 260 fails this test before it fails as a timeout, which is the difference between a defect with a name and a flaky job.

Two budget clamps live in the generators rather than only in the config validator, because a property test that generates a scenario longer than its own budget is a test that cannot pass. The scenario-horizon generator clamps at 60 simulated seconds for pacing-related properties, and the replication-count generator clamps at 8. `test_generator_clamps_are_present` asserts both clamps by inspecting the generator strategies, so removing a clamp fails immediately rather than at the next timeout.

#### F.7.3 Every test states its failure condition

Applying D-12, a test whose failure condition cannot be described is deleted and replaced. Three checks in this section are written specifically so they can fail, and each names the state of the world that fails it.

| Check                                | The observation that fails it                                                                         |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `sensor_readings_are_not_clamped`    | A reading that stays inside the declared validity range when the state is driven past it              |
| `telemetry_faults_physically_inert`  | Any difference in the physical KPI series between a telemetry-faulted run and a clean run at one seed |
| `draw_counts_invariant_under_faults` | Any per-stream draw count differing between a faulted and an unfaulted run                            |

The pattern is the same in all three: the test is constructed so that the passing state is a specific, reachable observation rather than the absence of an error.

## G. Open questions

These are genuinely undecided. Each names the options and the consequence of picking wrong, and none is papered over with an invented answer. An entry that gets decided keeps its number and records the decision in place, because a reader who follows a citation to G.11 needs to find the answer there rather than a gap.

**G.1 Whether to raise the cross-platform tier to byte identity.** The two-tier claim itself is settled by D-05 and stated in R1 and E.5: byte-identical on a pinned platform, value-equivalent across platforms inside a measured tolerance. What stays open is whether to close the gap. numpy's `log`, `exp`, and `erfinv` are SIMD-dispatched and can differ in the last bits across CPU microarchitectures and library builds, and inverse-CDF sampling puts them on the path of nearly every draw. Options: (a) keep the two tiers as they are; (b) vendor deterministic implementations of the inverse CDFs the catalog needs, which would make the cross-platform tier byte-identical too; (c) set `NPY_DISABLE_CPU_FEATURES` to a common baseline across the matrix and measure how much of the divergence that removes. Option (b) is a real implementation cost and needs its own correctness gate against a published reference, which is not free for `erfinv`. Option (c) is cheap and its value is unknown until measured, so the first step is the measurement rather than the decision. Unresolved.

**G.2 Rust device agent RNG parity, settled and its residual.** The derivation question is closed. Applying D-06, the agent derives its streams from the run seed and its device id through the same name-addressed derivation, specified byte for byte in A.7 in terms of BLAKE2b, numpy's SeedSequence mixing function, and the CM DXSM 128/64 variant that numpy calls `PCG64DXSM`, with a cross-language known-answer corpus and gate VG-VAR-07. The Rust side binds `rand_pcg::Lcg128CmDxsm64` at crate version 0.10 or later, which the crate documents as the same variant, so no vendored bit generator is needed. What the crate does not give free is the seeding: its `new` constructor steps the state with the cheap multiplier and numpy does not, so A.7 has the agent compute the seeded state itself and hand it to `from_state`. The residual open part is narrower and is genuinely open: the agent is a production-mode participant and does not join the single-process deterministic scheduler, so while its draws are reproducible and its emissions are ordered by the canonical `(sim_ts, producer_id, seq)` of D-07, the wall-time interleaving of its messages with the simulated fleet is not. Options: (a) accept that and score the agent's contribution under the value-equivalent tier only; (b) give the agent a simulation-mode transport that schedules its emissions on the sim clock, which makes the demo less honest about what an edge device is. Unresolved.

**G.3 Provenance of the parameter values.** Every numeric default in section B is engineering judgment. The family choices are separate and are sourced in B.13; this question is about the numbers inside them. No client data, employer data, or internal document may be used, which is a hard IP rule. Options: (a) ship judgment values clearly labelled as such; (b) fit what can be fitted to public datasets and cite them; (c) both, with a `source:` field per parameter taking `judgment`, `public_dataset:<citation>`, or `textbook:<citation>`. Option (c) is proposed, but the open part is how much of a 170-row catalog can be sourced, and whether a mostly-`judgment` catalog undercuts the reference-validation discipline established elsewhere. Two specific parameters are named here because each has a candidate published source that has not been checked: the Bass coefficients `p = 0.03` and `q = 0.38` in B.8, which sit close to values a published meta-analysis of diffusion applications is reported to give, and the learning rate `0.88` in B.9, whose curve form is Wright's (B.13 ref 22) but whose rate is not. Until those primary texts are read, both ship as judgment and are labelled as such. Unresolved.

**G.4 Residual correlation between quantities.** The catalog specifies marginals. Some correlation is handled structurally: worker random effects, the shared weather state, shared load driving temperature and current together. The residual correlation is currently independent by default, which understates the joint tail (the day when everything goes wrong at once is rarer in the model than in a real building). Options: (a) leave residuals independent and state the limitation; (b) add a Gaussian copula over a declared residual correlation matrix. A copula preserves the marginals, so the GoF suite still works, but the joint structure becomes much harder to test and the correlation matrix becomes a large, hard-to-justify config object. Unresolved.

**G.5 Which chart-selection mode is the headline number.** Section D.3 defines `empirical` and `declared` modes and reports both. The recommendation is that `empirical` is the published headline because `declared` gives the engine information no real deployment has. This needs an explicit decision because it changes every number in the README and the capability report, and reversing it later invalidates published comparisons.

**G.6 Compound fault instances.** When F-MECH-BEARING and F-CONV-JAM overlap on the same asset, is the truth two independent instances or one compound condition? The current rule keeps them independent and lets one alarm match one instance, which undercounts recall when a detector legitimately raises a single alarm for a compound condition. The `compound_group_id` field exists in the record for this purpose but its scoring semantics are not defined. Options: (a) keep instances independent and accept the recall penalty; (b) let one alarm satisfy every instance in a compound group; (c) score compound groups as their own class with separate metrics. Unresolved.

**G.7 `detectable_from` for non-scalar signatures.** The analytic noise-floor calculation works for a mean or variance shift on a scalar signal. It does not work for F-AMR-DEADLOCK, F-SORT-MISDIVERT, F-SEC-SPOOF, or F-EXO-WEATHER, whose signatures are structural or multivariate. Options: (a) compute `detectable_from` by an empirical calibration run per fault class and pin it in the scenario file; (b) omit the field for those classes and report MTTD only from `t_effect_start`, accepting that MTTD is then not comparable across fault classes; (c) define a class-specific detectability statistic per fault. Option (b) is the cheapest and the least informative. Unresolved.

**G.8 Truck arrivals after yard scheduling lands.** Today `variability.inbound.truck_interarrival` is an NHPP. Once E12 optimises appointment slotting, arrivals become appointment-plus-deviation, and the NHPP row applies only to the unappointed fraction. The proposal is `inbound.arrival_model: {poisson_process | appointment_plus_deviation}` with both rows present in the catalog and the scenario choosing. The open part is whether switching the default breaks the golden files and recorded runs from earlier phases, and whether that break is handled by the stream-versioning rule in A.3 or by a catalog major-version bump. Unresolved.

**G.9 Where out-of-range readings stop propagating.** R2 and R4 mean a sensor reading is never clamped, so a calibration-loss fault can emit -270 C. The proposal is that detectors read raw values while the metrics layer applies the declared validity range, excludes out-of-range samples from KPI computation, and raises a data-quality finding. The open question is whether that exclusion can hide a genuine fault signature from any KPI-based detector, and whether the dashboard renders the raw value, the excluded marker, or both. A wrong choice here either pollutes every KPI or silently suppresses a fault. Unresolved.

**G.10 Heavy tail shape parameters.** Generalized Pareto tails are used for in-transit shock magnitudes and acoustic emission amplitudes, and mean-reverting log processes are used for spot rates. For GPD shape `xi >= 0.5` the variance is infinite, and for `xi >= 1` the mean is infinite. Freight spot markets and cargo damage arguably live in that region. Bounding `xi` is a parameter choice rather than a truncation, so R3 permits it, but if `xi` is left high then the LSS engine's mean-based charts on those quantities are formally invalid and the capability numbers computed from them are meaningless. Options: (a) bound `xi` below 0.5 and state the modelling assumption; (b) permit high `xi` and make the engine select rank-based or quantile-based methods for those quantities, detected from the declared family. Option (b) is more honest and more work, and it interacts directly with G.5. Unresolved.

**G.11 PCG64 against PCG64DXSM. Decided 2026-08-09: `PCG64DXSM`.** The three options this question posed were (a) keep `PCG64` and hold the ceiling, (b) switch before Phase 0 closes, at the price of one coordinated change across four sections and no golden files, since none existed yet, and (c) switch later, at the price of regenerating every golden file plus a compatibility-table entry saying that no earlier recorded run reproduces. The owner took option (b).

The reason is the arithmetic in A.1a rather than a preference. numpy documents that a pair of `PCG64` streams sharing their lower 58 state bits fails PractRand when interleaved, that a seeded increment adds no protection against it, and that thousands of streams are comfortable while millions are the point to consider `PCG64DXSM` (B.13 ref 15). This section's declared ceiling of 750,000 streams sits between those ranges, and the computed expectation at that ceiling was `9.8e-7` colliding pairs. That is small and it is not nothing, and it was the only number in this document that argued for its own ceiling.

The deadline was the corpus freeze, not the end of Phase 0. Task 9 of the Phase 0a plan writes `tests/fixtures/rng_kat.json`, which is the first golden artefact in the repository, and the Rust crate is tested against that same file in Phase 1. Before the freeze the switch costs a document edit. After it, the switch costs a regenerated corpus. After the Rust crate lands, it costs a coordinated change in two languages against a corpus that is by then the evidence that they agree. So the decision was taken while it was still free.

What changed with it: A.1 and its alternatives discussion, the collision table and the ceiling rationale in A.1a, the lint text in A.4, the manifest fields in A.6, the whole of A.7 point 3 and the Rust binding, refs 15 and 24 in B.13, gate VG-VAR-07, and the matching statements in the foundations, roadmap, fleet, and twin sections. What did not change: the derivation of A.1, the stream grammar of A.2, the seeded state and increment, and every draw-order rule. Resolved.

**G.12 The maintainability lognormal.** Repair and clear durations in B.4 and B.6 use a lognormal, justified structurally: diagnosis time, part availability, and access multiply, so the log is a sum (B.13 ref 5). The maintainability literature is widely reported to prefer the lognormal for corrective maintenance time, and a defence handbook is the usual citation, but no primary text was retrieved for that claim, so it is not stated as fact anywhere in this section. Options: (a) leave the structural argument as the whole justification, which is defensible and slightly thin; (b) get MIL-HDBK-472 or an equivalent primary source and add a gate on a published repair-time example; (c) fit the family to a public maintenance dataset and cite the fit. Unresolved.

**G.13 Whether a contested ratio may drive incident generation.** B.9 generates incidents from near misses at a configurable `1/300`, attributed to Heinrich's ratio through a single secondary source (B.13 ref 11), whose primary text was not retrieved. The ratio is contested in the safety literature, and a twin that reports a TRIR built on it inherits the contest. Options: (a) keep the ratio, keep it in config, and print the value used in every safety report, which is the current position; (b) retrieve the primary text and a modern critique, and ship both with the figure; (c) replace the fixed ratio with a hazard model whose parameters are fitted to a public injury dataset, which removes the pyramid assumption at the cost of a fitted layer nobody asked for. The capability report currently prints the ratio it used, so the assumption is visible either way. Unresolved.

**G.14 No published birthday bound for PCG64DXSM.** Owner: John Ragon Hall, the repository owner, who also owns G.11. The `PCG64` bound of A.1a rested on a published number, the empirically determined 58 shared low bits and the `2^29` streams the birthday calculation gives from it. numpy publishes no matching number for `PCG64DXSM`. What it publishes is qualitative: collisions need two streams close in both the 128-bit state space and the 127-bit increment space at once, which it calls "less likely than the negligible chance of colliding in the 128-bit internal SeedSequence pool" (B.13 ref 15). A.1a thus states the residual as bounded above by the 128-bit pool collision it already computes, and invents no `PCG64DXSM` figure. Two consequences are open. The stream-count ceiling of 750,000 no longer has a statistical basis and is retained as an operating limit, so what number belongs there is undecided. And the ceiling test in the registry now asserts pool arithmetic, which would pass at any plausible catalog size, so it no longer fails for the reason it was written. Options: (a) leave both as they stand and keep the operating ceiling, which is the current position; (b) read the PCG author's own DXSM analysis and the PractRand results numpy cites, and state a bound from a primary text if one exists; (c) measure it here, which this repository may not do, because R9 forbids the repository being a reference for itself. Option (b) is the only one that can close it. Unresolved.
