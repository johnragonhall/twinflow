Status: design spec, implementation contract.

Owner: this section defines every package, event, config key, and test that produces telemetry

D-14, and every place this section applies one names the ruling id.

## 2. Packages

Nine Python bricks and one Rust crate. Every one has its own README, its own tests, and its own
`pip install` (or `cargo add`) path. A reader who wants only a physics-informed synthetic sensor
generator, or only a Sparkplug B codec, takes one and leaves the rest.

The dependency DAG is enforced in CI by `import-linter` with a layered contract in
`.importlinter`. A package may import the public API of a package strictly below it. No package
imports another package's private modules (anything under a `_` prefix). Communication between
subsystems that are not in an ancestor relationship happens only through versioned events in
`/schemas`.

That reading of the locked architecture constraint is granted by D-09, which rules that every
public symbol has exactly one owning package and that other packages import it rather than
redeclare it. ARCHITECTURE.md carries the amendment in one sentence: the versioned schema
registry is the only interface between subsystems, and a downward public-API import inside one
subsystem's own DAG is a layering fact the import-linter contract states and tests.

```
twinflow-kernel                (owned by the core section: Clock, Rng, Network, EventBus, Storage)
   |
   +-- twinflow-contracts      (pydantic value types shared by every brick above)
         |
         +-- twinflow-sparkplug   (contracts + protobuf)
         +-- twinflow-sensors     (contracts)
         +-- twinflow-rf          (contracts)
         +-- twinflow-buffer      (contracts)
               |
               +-- twinflow-pdm     (sensors, buffer)
                     |
                     +-- twinflow-device  (sensors, sparkplug, rf, buffer)
                     +-- twinflow-edge    (sparkplug, buffer, pdm)
                           |
                           +-- twinflow-fleet (contracts, sparkplug, edge, buffer)
```

Three edges in that graph are deliberate corrections and each one is tested.

`twinflow-buffer` exists because a device's RAM ring buffer and a gateway's disk-backed spill
are the same object with a different capacity, and because the tier-0 deadband runs on the
device while the tier-1 aggregation runs on the gateway. Putting `StoreAndForward`,
`DeadbandPolicy`, and `AggregationPolicy` in a brick below both is what lets 5.6 say "same
interface, different `cap_bytes` and a `spill_path`" without `twinflow-edge` importing a
sibling.

`twinflow-edge` sits above `twinflow-pdm` because `LocalInferenceHost` runs `EwmaResidual` at
tier 1, and `EwmaResidual` is owned by `twinflow-pdm` (D-09: one owner, imported not
redeclared).

`twinflow-fleet` does not depend on `twinflow-device`. The registry, the health scorer, and the
campaign engine consume `iot.device.*` and `fleet.*` events plus the pydantic models in
`twinflow-contracts`. Pulling the connection state machine, an MQTT client library, and
`cryptography` into the server brick would break A1's promise that a reader takes one brick and
leaves the rest. `test_fleet_imports_no_device_module` asserts it, and the import-linter
contract lists `twinflow-device` as forbidden from `twinflow-fleet`.

`twinflow-sensors` does not import `twinflow-rf`. The `rf_read_zone` signal-model kind is
registered by `twinflow-rf` through the `twinflow.signal_models` entry-point group, so the
catalog names a kind that `twinflow-sensors` resolves from the plugin registry at load time and
never imports. `test_sensors_has_no_rf_import` asserts it, and the import-linter contract lists
`twinflow-rf` as forbidden from `twinflow-sensors`.

`twinflow-device-agent` (Rust) sits beside `twinflow-device` and shares only wire formats and
test vectors, never source.

### 2.1 `twinflow-kernel` (dependency, not owned here)

This section consumes five ports and needs them to exist before Phase 1 work starts. Two of
them carry requirements this section is raising on the core section now, because the tests in
7.1 are unimplementable without them.

```python
class Clock(Protocol):
    def now(self) -> SimInstant: ...            # sim-time, monotone
    def sleep(self, seconds: float) -> Awaitable[None]: ...
    def at(self, t: SimInstant) -> Awaitable[None]: ...
    def wall_mapping(self) -> WallMapping: ...  # recorded in the provenance sidecar (C2, D-01)

class Rng(Protocol):
    def stream(self, name: str, **template_args: str) -> Generator: ...
    # name-addressed, per docs/design/variability-and-faults.md A.1 and A.4

class Network(Protocol):                        # MQTT-shaped port (D-08)
    async def resolve(self, host: str) -> list[Address]: ...
    async def tcp_connect(self, addr: Address, port: int) -> Socket: ...
    async def tls_handshake(self, sock: Socket, profile: TlsProfile) -> TlsLink: ...
    async def mqtt_connect(self, link: TlsLink | Socket, opts: MqttOptions) -> MqttSession: ...
    # MqttOptions carries retain, qos, last will, wildcard subscribe
    # simulation mode implements partition, latency, reorder, duplicate, idle-kill

class EventBus(Protocol):                       # subject-addressed fan-out (D-08)
    async def publish(self, subject: str, payload: bytes) -> None: ...
    async def subscribe(self, subject: str) -> AsyncIterator[bytes]: ...

class Storage(Protocol):
    def open_append(self, name: str) -> Appender: ...
    def open_kv(self, name: str) -> KeyValue: ...   # device NVS analog
```

D-08 splits the ports and this section binds to both halves. The device fleet and Sparkplug
always use `Network`, because Sparkplug B v3.0.0 death certificates ride on the MQTT last will
and testament and a subject-addressed bus has no last will. Analytics fan-out from the fleet
layer uses `EventBus`.

The four-rung diagnostic ladder in 5.11 is why `Network` exposes `resolve`, `tcp_connect`,
`tls_handshake`, and `mqtt_connect` as separate calls rather than one `connect`. A single
`connect` cannot produce a `dns_nxdomain` result distinct from a `tcp_timeout` result, and the
thirteen-value classification enum plus its per-classification unit tests depend on exactly
that distinction. This is a requirement on the core section, raised here because the core
section freezes its ports at Phase 0.

The RNG mechanism is not defined here. `docs/design/variability-and-faults.md` A.1 fixes it as
a content-addressed BLAKE2b spawn key feeding a numpy `SeedSequence` and a `PCG64` bit
generator, and A.2 fixes the stream-name grammar. This section declares its stream names in
5.29 against that grammar and nothing else. D-06 binds the Rust agent to the same derivation
byte for byte, and VG-IOT-02 is the cross-language conformance gate.

### 2.2 `twinflow-contracts`

Purpose: the pydantic value types that more than one brick needs, held in a leaf package so no
brick has to import a heavier sibling to name a type (D-09, D-10).

Public API:

```python
from twinflow.contracts import (
    DeviceRecord, EdgeNodeRecord, DeviceSpec, EdgeNodeSpec,
    LifecycleState, Quality,      # GOOD | UNCERTAIN | BAD | SUBSTITUTED (OPC UA style)
    HealthScore, FmeaRating, ActionPriority,
    ResourceSelector,             # the attaches_to grammar, 3.9
    AuthorityTier,                # L1 advise | L2 recommend | L3 auto-apply (E5 stub)
    CapabilityId, CapabilityRegistry,
    RunbookRef, SignatureId,
)
```

Depends on: `pydantic>=2`. Nothing else. A CI job installs it alone in a clean environment and
imports it (D-10).

`AuthorityTier` lands here as a three-value enum with E5a's autonomy metadata at P1, and the
append-only decision register it writes to arrives with E21a at the ECON phase. Both precede
E44's reconciliation work at P6-W1, so 5.19's `accept` action has its authority tier and its
register when it is written. No resequencing is needed, and section 8 records the trace.

### 2.3 `twinflow-sensors`

Purpose: the sensor catalog as data, the physics-informed signal models that read it, and the
fault transforms that corrupt the clean signal.

Public API:

```python
from twinflow.sensors import (
    Catalog,              # Catalog.load(path) -> Catalog ; .entry(type_id) ; .entries_by_category()
    CatalogEntry,         # frozen pydantic model, the schema in 3.1
    Channel,
    SignalModel,          # Protocol; sample(ctx) -> ChannelSample
    SampleContext,
    ChannelSample,        # clean_value, observed_value, unit, quality, fault_tags
    register_signal_model,  # decorator; also an entry-point group
    FaultTransform,       # Protocol; apply(sample, params, ctx) -> ChannelSample
    register_fault_mode,
    FaultInjector,        # schedules fault activation from the materialised schedule
    MsaProfile,           # repeatability and reproducibility variance components
)
```

Entry-point groups so a third party extends the catalog without forking:

```toml
[project.entry-points."twinflow.signal_models"]
my_kind = "mypkg.models:MyModel"
[project.entry-points."twinflow.failure_modes"]
my_mode = "mypkg.faults:MyFault"
```

Depends on: `twinflow-kernel`, `twinflow-contracts`, `numpy`, `ruamel.yaml` (needed for line
and column marks, see section 6).

Standalone value: a physics-informed synthetic sensor generator with a declarative catalog and
a fault library. Usable with no MQTT, no twin, and no broker.

```python
from twinflow.sparkplug import (

```

Depends on: `twinflow-kernel`, `twinflow-contracts`, `protobuf`. The `sparkplug_b.proto` file is
vendored under its own EPL-2.0 licence into `schemas/iot/sparkplug/`, recorded in

The version claim is verified. The Eclipse Sparkplug specification revision history lists

<https://sparkplug.eclipse.org/specification/>, HTTP 200, and the document PDF from
<https://sparkplug.eclipse.org/specification/version/3.0/documents/sparkplug-specification-3.0.0.pdf>,

### 2.5 `twinflow-rf`

Purpose: RF physics and read-zone geometry for UHF RFID. Link budget, antenna patterns,
polarization, tag orientation, dwell time, collision, interference, cross-reads, and missed-read
cause attribution.

Public API:

```python
from twinflow.rf import (
    Antenna, AntennaPattern, ReadZone, Portal,
    TagModel,             # sensitivity, backscatter loss, pattern, polarization
    PathLoss,             # exponent n, free-space closed form, fading model
    link_budget,          # -> forward_margin_db, reverse_margin_db
    read_probability,     # (tag_pose, speed, tag_count, interference) -> p, cause
    MissCause,            # OUT_OF_RANGE ORIENTATION_NULL OCCLUSION COLLISION SPEED INTERFERENCE
    simulate_pass,        # a pallet passing a portal -> list[ReadEvent]
    cross_read_candidates,
    RegulatoryLimits,     # per-region, per-band ceilings; see VG-IOT-04
    PhysicalConstant,     # value plus a mandatory `source` string; see INV-RF-6
    PlacementProblem,     # antenna placement, aim, and power as a search space
    diagnose,             # the physics-versus-device decision rule of 5.25
)
```

It registers the `rf_read_zone` signal-model kind through the `twinflow.signal_models`
entry-point group. That is the whole coupling to `twinflow-sensors`, and it runs in the
direction sensors to registry to rf, never sensors to rf.

Depends on: `twinflow-kernel`, `twinflow-contracts`, `numpy`. Optuna is an optional extra
(`twinflow-rf[search]`) because only `PlacementProblem` needs it (D-10).

Standalone value: high and rare. Almost nobody publishes a read-zone model.

### 2.6 `twinflow-buffer`

Purpose: the rate-reduction and durability primitives that a device and a gateway both need.
One implementation, two capacities.

Public API:

```python
from twinflow.buffer import (
    StoreAndForward,      # ring buffer with cap_bytes, drop policy, dropped counter
    SpillingStoreAndForward,   # the same, with a disk-backed spill beyond RAM
    DropPolicy,           # OLDEST | NEWEST
    DeadbandPolicy,       # absolute | percent | none, with max_publish_interval_s
    AggregationPolicy,    # window stats for high-rate channels
    BufferCounters,       # generated, published, dropped, buffered, deadbanded
)
```

Depends on: `twinflow-kernel`, `twinflow-contracts`.

`BufferCounters` carries the five terms INV-SF-1 balances, including `deadbanded`. A deadband
that suppresses a publish is a fifth disposition of a generated record, not an invisible one,
and making it a counted term is what lets 5.17 report the suppression rate as a measurement
rather than a config restatement.

### 2.8 `twinflow-pdm`

Purpose: predictive maintenance. Feature extraction, trend detection, time-to-threshold with
intervals, and the statistical-baseline-versus-learned-model bakeoff.

Public API:

```python
from twinflow.pdm import (
    FeatureWindow, extract_features,
    DutyCycleRegression,  # OLS on the twin-state design matrix; the residual is the health signal
    OrdinaryLeastSquares, # slope, intercept, residual standard deviation; gated by VG-IOT-09
    MannKendall,          # S, tau, p (nonparametric monotone trend test)
    TheilSen,             # slope, intercept, slope CI
    EwmaResidual,         # EWMA on the duty-cycle-corrected residual
    TimeToThreshold,      # estimate(level, slope_ci, limit) -> Interval
    BandEnergy,           # 1x/2x/3x, BPFO/BPFI/BSF/FTF band energies
    IsolationForestDetector,
    Bakeoff,              # runs all detectors on labelled incidents, publishes the table
    DetectorReport,       # pr_auc, mttd_p50, mttd_p90, fp_per_device_week, horizon
)
```

`OrdinaryLeastSquares` is the estimator VG-IOT-09 gates. It is not decoration: the duty-cycle
correction in 5.14 step 1 subtracts a twin-state-conditional expected value, and that
conditional expectation is an ordinary least squares fit against a design matrix of twin-state
indicators. It also serves as the parametric comparator against which `TheilSen` is judged on
the same series, which is how the bakeoff shows robustness earning its place rather than
assuming it.

Depends on: `twinflow-sensors`, `twinflow-buffer`, `twinflow-kernel`, `twinflow-contracts`,
`numpy`, `scipy`. `scikit-learn` is the extra `twinflow-pdm[learned]`, because only
`IsolationForestDetector` and the RUL regressor need it (D-10).

Standalone value: high. A trend-to-threshold PdM kit validated against published statistical
references is a self-contained thing.

### 2.11 `twinflow-device-agent` (Rust crate)

Purpose: satisfies component 2's "one device agent in Rust", and is the same code that runs on
the ESP32 for E47.

Modules: `state`, `timegate`, `backoff`, `sf`, `diag`, `boot`, `sparkplug`, `provision`, `ota`,
`transport`, `rng`.

Two build targets from one source:

- `--features host` links `tokio`, `rumqttc`, and `rustls`. It joins the simulated fleet as a
  normal edge node.
- `--features esp32` builds against `esp-idf-svc` (std-capable ESP-IDF bindings), giving Wi-Fi,
  SNTP, mbedTLS, NVS, and the native OTA partition API.

`esp-hal` (`no_std`) is recorded as the considered alternative and rejected: TLS, SNTP, and OTA
rollback would all have to be hand-rolled, which buys nothing for this repo's purpose.

Determinism: the crate is generic over `trait Clock`, `trait Rng`, and `trait Transport`. The
`sim` feature swaps in deterministic implementations driven by the same name-addressed
derivation the Python side uses, specified in `docs/design/variability-and-faults.md` A.1 and
bound by D-06. VG-IOT-02 gates the derivation against external known-answer vectors in both
languages, and IC-IOT-03 gates the state-machine transition traces and encoded payloads against
the shared parity corpus.

D-05 scopes what parity means, and this section claims neither more nor less. The cross-language
claim is exact on the integer half and tolerance-bounded on the float half. Bit generator output,
slot-counter draws, `bdSeq` and `seq` values, state-machine transition traces, and encoded
Sparkplug frames are byte-identical between the Python and Rust agents, because every one of them
is an integer or a byte string and no floating-point rounding stands between the seed and the
result. Continuous channel values are value-equivalent: the two implementations agree within a
tolerance derived from the divergence VG-IOT-02 measures across the supported platform set, and
the gate reports the observed maximum divergence rather than asserting a number chosen in
advance. When the observed maximum exceeds the recorded tolerance, the gate names which of the
two explanations applies, a wrong tolerance or a real defect, and fails either way. Byte-identical
whole-run equality holds on one pinned platform with one pinned dependency set, which is the
first tier of D-05, and nothing in this section claims byte-identity across platforms.

Published to crates.io by the same automated release job as the Python bricks (C9).

Invariants on the catalog, all CI-enforced and all named in 7.2:

- `type_id` is unique across all category files, and `category` is a scalar. An entry lives in
  exactly one category file. A subsystem in another category that consumes the entry expresses
  that through `attaches_to`, and 3.9 holds the consumption table.
- Every entry has at least one channel, at least one failure mode across channels plus device
  faults, and a non-empty `capability_unlocks`.
- Every `capability_unlocks` id resolves in `catalog/capabilities.yaml`, and every capability
  registered there names the module or the test that realises it (INV-CAT-4).
- Every channel carries the uniform quartet the source asks for: `unit`, a `baseline` block, a
  `noise` block, and a `drift` block. `drift` may be `{kind: none}` only with a `why` string,
  so an entry cannot silently have no drift characteristic (INV-CAT-1).
- Every channel carries an `msa` block with `repeatability_sigma` and `reproducibility_sigma`,
  or an explicit `msa_note` excluding it, so the LSS engine's Gage R and R study has declared
  variance components to be scored against.
- Every `unit` resolves in the published Unified Code for Units of Measure code list. The pinned
  edition is UCUM version 2.2, read from <https://ucum.org/ucum> on 2026-08-09, HTTP 200. The
  version is recorded in `catalog/UCUM_VERSION`, VG-IOT-05 is the gate, and a UCUM release that
  retires a code twinflow uses fails that gate rather than silently changing meaning.
- `(attaches_to, uns_parameter)` is unique, so no two channels collide on a UNS topic.
- `warn_limit < alarm_limit < trip_limit`, and all inside `range`.
- Every `signal_model.kind` and `failure_modes[].kind` resolves in the plugin registry, and
  every `failure_modes[].catalog_id` resolves in the fault catalog of
  `docs/design/variability-and-faults.md`.
- Every entry has a `phase`, and that phase exists in ROADMAP.md.
- Every entry with numeric alarm limits carries a `limit_source` string.
- No collection the catalog loader builds is a `set` (D-03). `Catalog.entries_by_category()`
  returns categories in the enumerated category order and entries sorted by `type_id`,
  `capability_unlocks` and `device_faults` keep their YAML declaration order, and the loader
  sorts any collection it derives from a mapping before it is iterated. INV-CAT-7 loads the
  shipped catalog twice in separate processes under different `PYTHONHASHSEED` values and
  asserts the two binding orders and the two resulting Sparkplug alias tables are identical,
  which is the observation that fails if a set reaches the alias assignment.

The `capability_unlocks` rule is what stops the catalog padding toward 500 thin entries, and it
is enforced rather than asserted. `catalog/capabilities.yaml` holds one row per capability with
the module path or test id that realises it, and a capability with neither is a load error
naming the capability. An entry that unlocks nothing cannot be merged, and an entry that claims
a capability nothing implements cannot be merged either.

### 3.3 `EdgeNodeSpec`, `DeviceSpec`, and `DeviceRecord`

Sparkplug has three identifier levels and this section maps each one to a distinct object,
because conflating the middle two is how a fleet quarantines itself.

A Sparkplug edge node is a process holding exactly one MQTT client session. It publishes
NBIRTH, registers its NDEATH as the last will, owns the `bdSeq` and `seq` counters and the
alias table, and hosts one or more Sparkplug devices. A Sparkplug device is a logical child of
that node, addressed as `{edge_node_id}/{device_id}`, and it is not an MQTT client. It has no
session, no `bdSeq`, and no last will of its own.

`EdgeNodeSpec` is the process, and `DeviceSpec` is the thing attached to it.

| Field                | Type                                | Invariant                                                          |
| -------------------- | ----------------------------------- | ------------------------------------------------------------------ |
| `edge_node_id`       | `str`, `^[a-z0-9][a-z0-9-]{2,63}$`  | unique across the fleet; one MQTT client session (INV-SPB-1)       |
| `area`, `line`       | `str`                               | render the Sparkplug `group_id` and `edge_node_id` templates       |
| `agent`              | `python` \                          | `rust`                                                             |

| `mqtt_client_id`     | `str`                               | derived from `edge_node_id`; a duplicate is a config error         |
| `devices[]`          | `list[device_id]`                   | non-empty; every id resolves in `devices.instances`                |

fields live on the device rather than the node because a HIL device is one physical board
hosting one Sparkplug device, and because the OTA campaign selector in 5.20 targets devices.
When an edge node hosts several simulated devices in one process, the campaign engine groups
them by `edge_node_id` and applies one image per process; `test_ota_groups_by_edge_node`
asserts it.

`test_two_agents_on_one_edge_node_is_rejected` writes a `facility.yaml` declaring two agent
processes claiming the same `edge_node_id` and asserts the loader refuses it with the offending
line and column. The failure is caught at validation, not discovered at runtime by the
`duplicate_client_id` quarantine path in 5.9.

### 3.4 Lifecycle states

Registry-side lifecycle, distinct from the agent's connection state machine in 5.1:

`unprovisioned -> enrolled -> healthy -> degraded -> failed -> quarantined -> retired`, plus the
orthogonal flags `updating` and `held`.

Transition rules:

- `healthy -> degraded` when `health_score < fleet.health.degraded_below` sustained for
  `fleet.health.dwell_s`.
- `degraded -> healthy` when `health_score >= fleet.health.recovered_above` sustained for the
  same dwell. The 5-point hysteresis band plus dwell is what stops flapping, and INV-HS-6
  asserts a bounded transition count under a constant fault.
- `* -> failed` when `health_score < fleet.health.failed_below` or a mode with `severity >= 9`
  is active.
- `* -> quarantined` on a compliance violation with `action: quarantine`, on a revoked
  certificate, or on a `duplicate_client_id` detection. A quarantined device's publishes are
  refused by broker ACL, not merely ignored.
- `-> retired` only by explicit operator action, which revokes the certificate.

All four thresholds read from 6.7 and all reference the score defined in 5.13.

### 3.6 FMEA rating tables

Five data files, all versioned, all replaceable by an adopting organisation.

`fleet/severity.yaml` maps `mode_id` to S. It is sourced from the catalog entry's `severity` and
mirrored here so a deployment can override without editing the catalog.

`fleet/occurrence_table.yaml` holds ten bands mapping a measured incident rate (incidents per
device-hour, or per opportunity for event-driven modes) to O in 1 to 10. It is a deterministic
function of measurement, not of judgement.

`fleet/detection_table.yaml` maps `MTTD_p90 / pf_interval` to D in 1 to 10. Detecting inside 1%
of the P-F interval rates D=1; detecting only after functional failure rates D=10.

`fleet/occurrence_prior.yaml` and `fleet/detection_prior.yaml` hold the cold-start values used
before a device has enough history for the measured tables, with the confidence penalty each
prior carries. 5.13 defines when they apply and when they are replaced.

Grounding D in the P-F interval is what turns the detection rating from a workshop guess into a
measured ratio, and the simulation is the only place where the P-F interval is known exactly.
The P-F interval concept is cited to Nowlan and Heap, "Reliability-Centered Maintenance", United
States Department of Defense, 1978, DTIC accession AD-A066579. The DTIC record refused
automated retrieval on 2026-08-09 (HTTP 403), so this citation is carried at single-source
confidence with the attribution stated in text, and open question 9.16 tracks getting an
accessible primary copy.

Invariants: the radiated power computed from `tx_power_dbm`, `peak_gain_dbi`, and `cable_loss_db`
must not exceed the ceiling for the declared `(region, band)` pair, and config validation refuses
otherwise. `zone_length_m > 0`. `sensitivity_dbm < 0`. VG-IOT-04 is the gate over the ceilings.

The ceilings are read from the two regulations, not chosen here. Each carries its own quantity,
and `RegulatoryLimits` stores the quantity and the number, because comparing a conducted
limit against an effective radiated power is the mistake that makes a compliance check useless.

| `(region, band)`     | Ceiling                                                    | Quantity                        | Source clause                                 |
| -------------------- | ---------------------------------------------------------- | ------------------------------- | --------------------------------------------- |
| `fcc, us_902_928`    | 1 W, with antenna directional gain at most 6 dBi           | peak conducted output power     | 47 CFR 15.247(b)(2) and 15.247(b)(4)          |
| `etsi, eu_865_868`   | 33 dBm in a 200 kHz bandwidth                              | effective radiated power        | ETSI EN 302 208 V3.3.1 clause 4.3.3.3.1       |
| `etsi, eu_915_921`   | 36 dBm in a 400 kHz bandwidth                              | effective radiated power        | ETSI EN 302 208 V3.3.1 clause 4.3.3.3.2       |

47 CFR 15.247 was retrieved 2026-08-09 from the eCFR renderer API for title 47, section 15.247,
HTTP 200. Paragraph (b)(2) reads "For frequency hopping systems operating in the 902-928 MHz
band: 1 watt for systems employing at least 50 hopping channels", and paragraph (b)(4) bases that
limit "on the use of antennas with directional gains that do not exceed 6 dBi", requiring a
dB-for-dB conducted-power reduction above 6 dBi. `PlacementProblem` treats FCC transmit
power and antenna gain as one coupled constraint rather than two independent ceilings.

ETSI EN 302 208 V3.3.1 (2020-08) was retrieved 2026-08-09 from the ETSI deliverable server, HTTP
200. Its title states power levels up to 2 W in 865 MHz to 868 MHz and up to 4 W in 915 MHz to
921 MHz, and clauses 4.3.3.3.1 and 4.3.3.3.2 give those as 33 dBm and 36 dBm effective radiated
power in the stated bandwidths.

Clause 4.3.4.3 of the same standard couples beam-width to radiated power, and the model carries
that coupling because an antenna configuration can satisfy the power ceiling and still be
illegal. In the lower band there is no beam-width restriction at or below 500 mW e.r.p.,
beam-width must be at most 180 degrees above 500 mW up to 1000 mW, and at most 90 degrees above
1000 mW up to 2000 mW. In the upper band the same three bands are at or below 1000 mW, above 1000
mW up to 2000 mW, and above 2000 mW up to 4000 mW. `Antenna.pattern` yields a horizontal
half-power beam-width, config validation refuses a combination that violates the coupling, and
VG-IOT-04 asserts both the power ceiling and the beam-width coupling against a table transcribed
from those clauses.

Every numeric physical constant in `twinflow-rf` is a `PhysicalConstant` carrying a mandatory
`source` string, in the same style the catalog requires `limit_source`. INV-RF-6 asserts that no
`PhysicalConstant` ships with an empty `source`, and the permitted source kinds are a named
published reference, a named regulation, or the literal string
`"repo-defined modelling assumption, not a measurement"`.

### 3.9 `ResourceSelector`, consumption, and the capability registry

`attaches_to` is a selector over the twin's resource tree, and its grammar is frozen at Phase 0
alongside `UnsPath` because catalog entries are written from Phase 1 onward and changing the
grammar later rewrites 80 files.

The grammar is a dot-delimited path of segments matching `^[a-z0-9][a-z0-9_-]{0,31}$`, where a
segment may be the literal `*` matching exactly one level, or the literal `**` matching one or
more levels, and only as a whole segment:

```
selector  := segment ( "." segment )*
segment   := name | "*" | "**"
name      := [a-z0-9][a-z0-9_-]{0,31}
```

The mapping to `UnsPath` is fixed and total. A resource path `area.line.equipment.subsystem`
resolves to the UNS path `{enterprise}/{site}/{area}/{line}/{equipment}/{parameter}`, where
`enterprise` and `site` come from the `uns:` block, the first three resource segments supply
area, line, and equipment, and any deeper resource segments are joined with `.` into the
Sparkplug metric name below `parameter`. `UnsPath.from_resource(path, parameter)` and
`UnsPath.to_resource()` are the two directions, and INV-UNS-1 covers the round trip.

The grammar is co-owned with the twin section, which owns the resource tree itself. This
section owns the selector syntax, the mapping, and the resolution test. INV-CAT-5 asserts that
every `attaches_to` in the shipped catalog resolves to at least one resource in each of the
three worked profiles from A2, and `just run --dry-run` fails with the unresolved selector
named.

Cross-category consumption lives here rather than in the category files, so that a type stays
in exactly one category:

| Entry                     | Owning category      | Also consumed by                                        |
| ------------------------- | -------------------- | ------------------------------------------------------- |
| `rtd_pt100`               | industrial_equipment | warehouse_logistics (dock and staging ambient probes)   |
| `load_cell_shear_beam`    | industrial_equipment | warehouse_logistics (in-motion checkweigh)              |
| `motor_current_signature` | industrial_equipment | electrical_power (energy per pallet, E7)                |
| `uwb_asset_tag`           | warehouse_logistics  | safety_compliance (worker proximity, 6a10)              |
| `ppe_compliance_cv`       | safety_compliance    | warehouse_logistics (the shared camera device, req 4)   |

`catalog/capabilities.yaml` is the registry every `capability_unlocks` id resolves against:

```yaml
capabilities:
  - id: rfid_read_counting
    realised_by: "twinflow.rf.simulate_pass"
    proven_by: "tests/rf/test_simulate_pass.py::test_pass_produces_read_events"
  - id: rf_read_zone_diagnosis
    realised_by: "twinflow.rf.diagnose"
    proven_by: "tests/rf/test_diagnose.py::test_physics_versus_device"
```

A capability with neither `realised_by` nor `proven_by` is a load error. That is what turns the
anti-padding rule from an assertion into a check: an entry can only claim a capability that
some module realises and some test proves.

## 4. Events

All schemas live in `/schemas/iot/` and `/schemas/fleet/` as JSON Schema 2020-12, registered per
C3, and additive-only within a major version.

Every event carries the envelope the schema registry defines. Per D-07 the envelope is
`event_id`, `schema`, `version`, `sim_ts`, `run_id`, `producer_id`, and `seq`, where `seq` is
dense per `(run_id, producer_id)` and the canonical total order over the log is
`(sim_ts, producer_id, seq)`. This section's producers are the edge node agents (one
`producer_id` per `edge_node_id`), the gateways (one per `gateway_id`), the fleet service, the
PdM service, and the fault injector. No producer in this section allocates a globally dense
sequence number, because no allocator for one exists.

The Sparkplug wire payload is protobuf, not JSON Schema. It is registered as
`/schemas/iot/sparkplug/payload.v3_0_0.proto` with `/schemas/iot/sparkplug/conformance.yaml`
alongside it, which enumerates the normative rule ids the codec claims to satisfy (see 7.4).

Identifier mapping, defined once in `UnsPath`:

- `group_id = "{enterprise}:{site}:{area}"`
- `edge_node_id = "{line}"`
- `device_id = "{equipment}"`

The `parameter` segment becomes the Sparkplug metric name, dot-delimited where nested.

Colons are the ISA-95 delimiter inside `group_id` because Sparkplug identifiers must not contain
`/`, `+`, or `#`. The full ISA-95 path is recoverable from the three identifiers, which INV-UNS-1
proves by round trip.

The default `edge_node_id` template renders the line, which means one agent process per line
hosts every device on that line. That default is only correct because 3.3 makes the edge node a
process and the device a logical child. Two devices on line `conv-02` are two Sparkplug devices
under one edge node and one MQTT client session, not two clients both claiming `conv-02`.
INV-SPB-1 asserts that no two MQTT client sessions in a run share an `edge_node_id`, and
`test_two_agents_on_one_edge_node_is_rejected` (3.3) catches the config that would break it
before the run starts.

A deployment that genuinely wants one process per device sets
`uns.sparkplug.edge_node_id_template` to `"{line}-{equipment}"`, and the validator then requires
`devices[]` on each edge node to have length one. Both shapes are legal; the shape that produced
a self-inflicted `duplicate_client_id` quarantine is not.

### 4.4 Telemetry and the ground-truth pair

`iot.telemetry.reading.v1` is the canonical internal reading. It is what the historian stores
and what every downstream package consumes. Sparkplug is the wire format; this is the semantic
record.

```json
{
  "device_id": "conv-02-motor-temp",
  "edge_node_id": "conv-02",
  "channel_id": "winding_temp",
  "uns_path": "acme/dc-01/sortation/conv-02/motor/winding_temp",
  "observed_value": 71.4,
  "unit": "Cel",
  "quality": "good",
  "device_ts": 1730000000.5,
  "ingest_ts": 1730000000.56,
  "clock_epoch_id": "conv-02-motor-temp:7",
  "seq": 41,
  "sparkplug_alias": 12,
  "replayed": false,
  "buffer_latency_s": 0.0
}
```

The ground-truth companion carries the answer key and never travels with the reading:

```json
{
  "reading_event_id": "01J8Z...",
  "device_id": "conv-02-motor-temp",
  "channel_id": "winding_temp",
  "clean_value": 68.9,
  "fault_tags": ["drift:thermocouple_junction_degradation"],
  "fault_instance_ids": ["F-DEV-DRIFT.0007"],
  "device_ts": 1730000000.5
}
```

`iot.telemetry.groundtruth.v1` is written only to the ground-truth Delta root and is joined to
the reading by `reading_event_id`. Separating the record rather than firewalling a column is
what makes 5.12's guarantee enforceable with the storage stack this repo actually locks in. The
clean value is never discarded, which is what makes MTTD exact, makes E25's labelled datasets
free, and makes the PdM bakeoff scoreable.

Three timestamps, three jobs, and the split exists to stop them being mixed:

`device_ts` is the device's own clock, which drifts. `ingest_ts` is the gateway's clock when the
record was accepted, which does not drift; it is arrival accounting and it feeds the ingest-lag
SLO. `clock_epoch_id` names the interval between two clock resyncs on one device, so a resync
step ends an epoch instead of violating monotonicity.

Both are sim-time (C2). `device_ts` and `ingest_ts` are seconds since the scenario epoch declared
in `simulation.epoch`, read from the injected `Clock`, and the values printed in the examples
above are sim-time seconds rather than a wall-clock reading that happens to look like one. D-02
permits a wall-clock read in exactly four places and none of them is a telemetry payload, so a
device or gateway that read the host clock to fill either field would be a determinism defect
rather than a modelling choice. `Clock.wall_mapping()` records the one sim-to-wall mapping per
run, and it lands in the provenance sidecar (D-01), never in an event. The nondeterminism gate in
`scripts/checks/nondeterminism-gate.sh` enforces the rule outside the kernel package, and
INV-CLK-4 asserts that no schema under `/schemas/iot/` or `/schemas/fleet/` marks a timestamp
field `x-wallclock: true` except the two the provenance sidecar owns.

The historian's ordering key within a channel is `(device_id, clock_epoch_id, device_ts)`.
`ingest_ts` is never an ordering key. That correction matters because 5.6 replays buffered
records with a fresh `ingest_ts`, so ordering by arrival would place hour-old outage data after
fresh data and an SPC chart over the outage window would be wrong. Ordering across producers is
the D-07 canonical total order `(sim_ts, producer_id, seq)`. INV-CLK-3 asserts that a record
buffered through an outage lands at its true position in its channel's series, and S-IOT-02
asserts it end to end by building an I-MR chart across the outage window and comparing the point
order against the ground-truth sample order.

`buffer_latency_s` is `ingest_ts - device_ts` for a replayed record, published so the ingest-lag
chart can separate a slow network from a recovering buffer.

## 5. Behaviour

### 5.1 Device agent state machine (component 2)

The state machine belongs to the edge node agent, because the states it names are session
states and the session is the node's. A Sparkplug device below a live node has two states,
present and absent, and the node publishes DBIRTH or DDEATH accordingly.

```
FACTORY_NEW --(has birth cred)--> TIME_SYNC_WAIT
TIME_SYNC_WAIT --(clock >= epoch_floor)--> PROVISIONING | CONNECTING
PROVISIONING --(operational cert issued)--> CONNECTING
CONNECTING --(CONNACK + NBIRTH sent)--> ONLINE
CONNECTING --(failure)--> CONNECTING (backoff) | HELD (after N)
ONLINE --(link loss)--> BUFFERING
ONLINE --(health signal)--> DEGRADED (still publishing)
BUFFERING --(reconnect)--> CONNECTING
BUFFERING --(buffer full)--> BUFFERING (drop per policy, counter increments)
* --(N consecutive failures)--> HELD
HELD --(hold expiry or link-up event)--> CONNECTING
ONLINE --(OTA command)--> UPDATING --(applied + verified)--> TIME_SYNC_WAIT (reboot)
* --(operator)--> DECOMMISSIONED
```

Every transition publishes `iot.device.state.v1`. The state machine is a pure function of
`(state, event, config)` and is the object the cross-language parity check compares
(IC-IOT-03): the Python and Rust agents must produce identical transition traces for the same
input trace.

### 5.2 Sampling and fault application

Each channel is a coroutine on the sim clock at its `publish_policy` cadence. Per sample:

1. Resolve `SubsystemState` from the twin through `attaches_to` (running, idle, faulted, speed,
   load) and `AmbientState` (facility temperature, humidity).
2. Call the registered `SignalModel.sample(ctx)` to produce `clean_value`.
3. Apply the ordered chain of `FaultTransform` for every active fault on this channel,
   producing `observed_value` and accumulating `fault_tags`. The chain order is the catalog
   declaration order, which is a list, never a set (D-03).
4. Apply quantization (`resolution`) and clipping (`range`), setting `quality = uncertain` on
   clip.
5. Apply the tier-0 deadband policy. A suppressed sample increments `deadbanded` on
   `BufferCounters` and is still written to the ground-truth stream, so INV-SF-1 balances and
   the suppression rate becomes a measured quantity rather than a config restatement.

RNG discipline follows `docs/design/variability-and-faults.md` rule R6: a fault transforms a
sample and never consumes a subsystem draw. The clean signal draws from
`sensor.<measurand>.<device_id>.noise`; a fault instance draws from
`fault.<fault_id>.<instance_id>.progression`. Two separate streams, so turning a fault on does
not shift the noise sequence of the clean signal and the with-fault and without-fault runs stay
comparable. INV-DET-2 asserts it for channel-level modes and INV-DET-3 asserts the weaker,
correct claim for device-level modes.

### 5.3 Device-type abstraction

The chain is catalog YAML, then `CatalogEntry`, then a `SignalModel` selected by `kind` from the
plugin registry, then a `Channel` bound to a `UnsPath`, then a Sparkplug metric with an alias.
Nothing in that chain is type-specific code. Adding type 300 touches one YAML file.

Signal models register two ways: the `@register_signal_model("kind")` decorator for in-repo
models, and the `twinflow.signal_models` entry-point group for out-of-repo models. Both
populate the same registry, and a duplicate `kind` is a hard load error naming both providers.
`twinflow-rf` registers `rf_read_zone` through the entry-point group like any third party
would, which is what keeps `twinflow-sensors` free of an RF import (2.5).

### 5.4 Sparkplug session management (E3)

On connect the edge node agent does the following, in order.

1. Increment `bdSeq` in NVS, which persists across reboots. A duplicate `bdSeq` after a reboot
   is a defect the boot record makes visible.
2. Register NDEATH as the MQTT last will, carrying that `bdSeq`.
3. CONNECT with clean session (MQTT 3.1.1) or clean start with session expiry 0 (MQTT 5.0).
   Sparkplug needs a fresh session; a persistent session would deliver stale queued messages
   after a birth certificate, breaking the state model.
4. Publish NBIRTH with `seq = 0`, carrying every node metric with its `DataType` and its alias
   assignment, plus `Node Control/Rebirth`, `bdSeq`, and the node properties (firmware version,
   hardware rev, boot record summary, `sf_dropped_records`).
5. Publish one DBIRTH per attached device, carrying every metric that device will ever publish.
   A metric absent from DBIRTH may never appear in DDATA. `ConformanceMatrix` enforces this at
   encode time, raising rather than publishing an invalid stream.
6. Thereafter publish NDATA and DDATA using aliases only, with `seq` incrementing modulo 256.

On `Node Control/Rebirth = true` through NCMD, republish NBIRTH and all DBIRTHs with the current
`bdSeq` and `seq` reset to 0.

`sf_dropped_records` is a Sparkplug metric on every NBIRTH and on change. The device tells the
fleet how much it lost, in band, on the same channel as the data. Loss is admitted, not hidden.

QoS and retain are configured per topic class, not fleet-wide. Component 6c asks for QoS levels
to be exercised, so the matrix is a real config surface. Every Sparkplug row is normative and its
value is read from the specification rather than chosen here:

| Topic class    | QoS | Retain | Normative identifier                                                          | Chosen here |
| -------------- | --- | ------ | ----------------------------------------------------------------------------- | ----------- |
| NBIRTH         | 0   | false  | `tck-id-payloads-nbirth-qos`, `tck-id-payloads-nbirth-retain`                 | no          |
| DBIRTH         | 0   | false  | `tck-id-payloads-dbirth-qos`, `tck-id-payloads-dbirth-retain`                 | no          |
| NDATA          | 0   | false  | `tck-id-payloads-ndata-qos`, `tck-id-payloads-ndata-retain`                   | no          |
| DDATA          | 0   | false  | `tck-id-payloads-ddata-qos`, `tck-id-payloads-ddata-retain`                   | no          |
| NCMD           | 0   | false  | `tck-id-payloads-ncmd-qos`, `tck-id-payloads-ncmd-retain`                     | no          |
| DCMD           | 0   | false  | `tck-id-payloads-dcmd-qos`, `tck-id-payloads-dcmd-retain`                     | no          |
| DDEATH         | 0   | false  | none: v3.0.0 states no QoS or retain rule for DDEATH                          | yes         |
| NDEATH as will | 1   | false  | `tck-id-payloads-ndeath-will-message-qos`, `-will-message-retain`             | no          |
| STATE birth    | 1   | true   | `tck-id-host-topic-phid-birth-qos`, `tck-id-host-topic-phid-birth-retain`     | no          |
| STATE as will  | 1   | true   | `tck-id-payloads-state-will-message-qos`, `-state-will-message-retain`        | no          |
| UNS mirror     | 1   | true   | none: the mirror is not a Sparkplug topic                                     | yes         |

Every value in the table was read from the Sparkplug B v3.0.0 specification text, retrieved
2026-08-09 (2.4). The four normative sentences that carry the surprises read, verbatim: "NBIRTH
messages MUST be published with the MQTT QoS set to 0"; "The NDEATH message MUST set the MQTT
Will QoS to 1 in the MQTT CONNECT packet"; "The NDEATH message MUST set the MQTT Will Retained
flag to false in the MQTT CONNECT packet"; and, for the host application, "The MQTT retain flag
for the Birth Certificate MUST be set to TRUE".

NDEATH is the one that surprises a reader who assumes data and death travel alike: the death
certificate is registered as the MQTT will at CONNECT with QoS 1 and retain false, while every
data and command message is QoS 0. NCMD and DCMD are QoS 0 by the specification, so a lost
command is recovered by the command's own acknowledgement in the payload, not by the transport.

DDEATH is the row with `Chosen here: yes`, and it is the only Sparkplug row that carries no rule
id. The v3.0.0 rule-id set contains QoS and retain rules for NBIRTH, DBIRTH, NDATA, DDATA, NCMD,
DCMD, the NDEATH will, and the STATE will, and none for DDEATH. Absence of a rule is not
permission to leave the value undeclared, so twinflow publishes DDEATH at QoS 0 with retain
false, matching its sibling device messages, and `conformance.yaml` records the row with
`rule_id: null` and `basis: repo choice, no v3.0.0 rule`. INV-QOS-2 asserts that every row whose
`rule_id` is null carries a written basis, which stops a future reader mistaking a repo choice
for a specification requirement.

The normative values per rule id live in `schemas/iot/sparkplug/conformance.yaml` as
`{rule_id, topic_class, qos, retain}` rows rather than scattered in code, and the config table
above is checked against them at load. INV-QOS-1 asserts that every configured
`transport.qos_by_topic_class` entry matches its `conformance.yaml` row, or names in
`transport.conformance_departures` the rule id it departs from. A departure with no named rule id
is a config error. The TCK is the arbiter for the normative half (7.4). See open question 9.1.

QoS 1 behaviour is exercised in two places rather than by breaking conformance silently. S-IOT-15
runs the same fleet and seed with the UNS mirror at QoS 0 and at QoS 1, asserts the business event
stream is identical under the documented normalization, and reports the measured redelivery count
at QoS 1, which is the number the `mqtt_redelivery` fault mode inflates. A second arm of the same
scenario declares a departure on `tck-id-payloads-ddata-qos`, publishes DDATA at QoS 1, and
asserts that `ConformanceMatrix` marks the run non-conformant and names the rule. Exercising QoS 1
and claiming Sparkplug conformance at the same time is the mistake that arm exists to catch.

### 5.5 UNS path algebra

One value object, two renderings, proven equal by round trip. `UnsPath` validates each segment
against `^[a-z0-9][a-z0-9-]{0,31}$` at construction, which is what makes both renderings safe:
no segment can contain a topic wildcard or a delimiter. Constructing a path with an illegal
segment raises with the offending segment named.

`UnsPath.from_resource` and `UnsPath.to_resource` connect it to the `ResourceSelector` grammar
in 3.9, so the dotted resource tree and the slash-delimited namespace are two views of one
hierarchy rather than two hierarchies. INV-UNS-1 covers all four directions.

### 5.6 Store-and-forward (component 6c)

A fixed-capacity ring buffer in RAM, sized in bytes, holding serialized records. One
implementation in `twinflow-buffer`, two capacities.

```
cap_bytes           default 65536 for a constrained device, 4 MiB for a gateway
drop_policy         oldest | newest          default oldest
high_water_pct      80    -> publishes a warning metric
replay_rate_msgs_s  200   -> paced replay, so a recovering fleet does not flood the broker
```

While `ONLINE`, records are published directly. A publish that fails locally (no link, TCP
error, broker refused) pushes the record into the buffer and moves the node to `BUFFERING`. On
overflow the buffer drops per policy and increments `sf_dropped_records`, and the counter is
published, so downstream analysis knows exactly how many records are missing and over what
interval. On reconnect, replay is paced at `replay_rate_msgs_s` and interleaved with live data.
Per-channel FIFO order is preserved (INV-SF-3). Replayed records keep their original `device_ts`
and their original `clock_epoch_id`, carry `replayed: true`, and take a fresh `ingest_ts` with
`buffer_latency_s` filled in.

Global order across channels is not preserved and is not claimed. Ordering within a channel is
`(device_id, clock_epoch_id, device_ts)` per 4.4, and ordering across producers is the D-07
canonical total order, so a replayed record lands in its true position rather than after the
fresh data that arrived while it was buffered.

A gateway (tier 1) uses `SpillingStoreAndForward`, which spills to disk beyond RAM, because a
gateway has a filesystem and a constrained device does not. Same interface, different
`cap_bytes`, plus a `spill_path`.

The disagreement between "Sparkplug data is QoS 0" and "kill the broker and lose nothing" is
resolved here, not by transport. When the broker dies the TCP connection breaks, the local
publish fails, and the record goes to the buffer. The guarantee comes from the buffer plus
session sequence numbers, not from QoS. ARCHITECTURE.md states that plainly beside the QoS
matrix in 5.4, which is worth more than raising the QoS would be.

### 5.7 The time gate

A device with no RTC boots at the Unix epoch. Two things break: TLS certificate validation fails
`notBefore`, and any token with an `iat` or `exp` is nonsense. Both failures are misdiagnosed as
certificate or credential problems by everyone who has not seen it before.

Rule: while `clock.now() < security.epoch_floor`, the agent will not start a TLS handshake, will
not mint or present a bearer token, and will not publish. It sits in `TIME_SYNC_WAIT`, runs SNTP
with its own backoff, and publishes `iot.device.timegate.v1` on entry and exit.

The shipped default floor is a fixed ISO8601 date recorded in `facility.yaml`, not the firmware
build timestamp. D-02 permits a wall-clock read in exactly four places, and none of them is a
config default that reaches an event payload; `iot.device.timegate.v1` carries `floor_epoch_s`
and is in the hashed tape, so a build-time wall-clock value there would make two runs of the
same seed differ. A fixed date also has a plainer virtue: 499 of 500 simulated Python devices
have no firmware build timestamp at all, so a build-timestamp default is undefined for almost the
whole fleet.

`security.epoch_floor: build_timestamp` remains available and is refused by config validation
unless `simulation.mode` is `production`, which covers the HIL path and a real deployment. In
that mode `floor_origin` is `build_timestamp`, the value is written to the provenance sidecar
(D-01), and the run manifest already records `deterministic: false` for any HIL run (5.26).

The gate has a ceiling too. `epoch_ceiling_years` (default 20) refuses an absurd future clock,
which is what a corrupted RTC produces.

INV-TG-1 asserts no handshake and no token mint below the floor, for any clock trajectory. A
mutation that removes the gate fails the test, which is the point.

The determinism carve-out is enumerated rather than described. `DETERMINISM_EXCLUDED_FIELDS` is
a frozen constant in the determinism harness listing every field excluded from the hash, and
INV-DET-4 asserts that the constant contains no field any schema marks `x-simtime: true` and
that every field it does contain is marked `x-wallclock: true` in its schema. A field cannot be
excluded from the hash without saying so in the schema, and a sim-time field cannot be excluded
at all.

### 5.8 Full-jitter exponential backoff

```
delay = uniform(0, min(cap_ms, base_ms * 2 ** attempt_index))
```

Base 500 ms, cap 60 s. The retry counter resets on a successful CONNACK plus `stability_s`
(default 30) online, never on CONNACK alone. Resetting on CONNACK alone is the defect that
produces a fast reconnect loop against a broker that accepts and immediately drops.

Full jitter, not equal jitter and not decorrelated jitter. Marc Brooker's AWS Architecture Blog
article "Exponential Backoff And Jitter", dated 04 March 2015, retrieved 2026-08-09 from
<https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/>, HTTP 200, compares
the three. It reports that equal jitter "does slightly more work than Full Jitter, and takes much
longer", and that against decorrelated jitter "The 'Full Jitter' approach uses less work, but
slightly more time". Full jitter is chosen for the lower client work, and the article does not
claim it is also fastest. The alternative forms are recorded in the module docstring
with the reason for the choice, and VG-IOT-14 reproduces the comparison.

The property that matters is the fleet-level one: devices coming back after a broker restart
must not stampede. `backoff.stampede_ceiling_per_100ms` is a real config key with a derived
default of `max(4, ceil(broker.max_inflight / 4))`, and INV-BO-2 asserts the maximum connection
attempts in any 100 ms bucket over the reconnect window stays under it. A mutation guard asserts
the same test fails when jitter is removed.

### 5.9 Reboot forensics and crash loops

Every boot publishes `iot.device.boot.v1` before anything else, including before the time gate
resolves, buffered if necessary.

`ResetReason` mirrors the ESP-IDF `esp_reset_reason_t` enumeration one to one. The enumeration
was retrieved 2026-08-09 from
<https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/misc_system_api.html>,
HTTP 200, and has sixteen members: `ESP_RST_UNKNOWN`, `ESP_RST_POWERON`, `ESP_RST_EXT`, `ESP_RST_SW`, `ESP_RST_PANIC`,
`ESP_RST_INT_WDT`, `ESP_RST_TASK_WDT`, `ESP_RST_WDT`, `ESP_RST_DEEPSLEEP`, `ESP_RST_BROWNOUT`,
`ESP_RST_SDIO`, `ESP_RST_USB`, `ESP_RST_JTAG`, `ESP_RST_EFUSE`, `ESP_RST_PWR_GLITCH`, and
`ESP_RST_CPU_LOCKUP`. The Python enum members are the same sixteen, lowercased with the
`esp_rst_` prefix removed, so `panic`, `int_wdt`, `task_wdt`, `pwr_glitch`, `cpu_lockup`, and
the rest. The simulated devices produce the same enum, so the fleet layer has one code path.
VG-IOT-13 asserts the member sets match exactly, which is how a future ESP-IDF release adding a
cause is caught as a test failure rather than as a silent `unknown`.

Four derived fleet signals, each with the detector that raises it:

| Signal               | Detection rule                                                                                                                                     | Raised mode                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Crash loop           | `boot_count` rises by at least `crash_loop_threshold` (default 5) within `crash_loop_window_s` (default 600) with `reset_reason` in the fault set  | `crash_loop`, severity floor 8 |
| Brownout correlation | `brownout_count` increments inside `brownout.tx_window_ms` of a transmit event above `brownout.tx_power_dbm_threshold`                             | `power_supply_sag`             |
| Heap exhaustion      | `free_heap_min_bytes` trends down across boots with `reset_reason = panic`                                                                         | `heap_leak`                    |
| Duplicate client id  | `bdSeq` increments faster than `iot.device.boot.v1` events arrive for the same `edge_node_id`                                                      | `duplicate_client_id`          |

The brownout model is stated as a relation with an assertion behind it, not as a story. The
simulated device draws `I_tx` from the configured transmit current curve and computes
`V_rail = V_supply - I_tx * R_supply`, and a brownout fires when `V_rail` falls below
`brownout.threshold_v`. All four constants are config keys with defaults labelled
"repo-defined modelling assumption, not a measurement", because no measured I-V curve for a
specific board is shipped here; open question 9.17 tracks getting one. INV-BRN-1 asserts that a
brownout event occurs only within `brownout.tx_window_ms` of a qualifying transmit event and
never in the absence of one, and `test_brownout_needs_tx` drives a device at zero transmit power
and asserts zero brownouts across a full sim day. The runbook's fix is supply decoupling, not
firmware, and it says so because the model says so.

Heap exhaustion earns its own signal because the distinction is what makes the runbook useful.
A panic with a flat `free_heap_min_bytes` trend is a code defect. A panic with a falling trend
across boots is a leak, and the fix is different.

Duplicate client id is the Sparkplug-native detection. Two edge nodes flashed with the same id
take the MQTT session from each other in a loop, and each takeover forces a new session without
a reboot, so `bdSeq` outruns the boot events. The fleet layer records this as
`bdseq_without_boot` and raises `duplicate_client_id`, which quarantines both. It is a real
failure that costs days to diagnose in the field, and 3.3 plus INV-SPB-1 make sure the repo's
own default config cannot cause it.

### 5.10 Hold-after-N

After `hold_after_consecutive_failures` (default 5) consecutive connect or publish failures, the
agent enters `HELD` for `hold_duration_s` (default 900) rather than rebooting. It runs the
diagnostic ladder once on entry, writes the result to NVS, buffers telemetry, and stays
reachable to the local network so an engineer can pull the bundle. It leaves `HELD` early on a
link-layer up event.

Rebooting on repeated failure is the default that produces a fleet of devices that are
permanently rebooting and so permanently undiagnosable, and it also destroys the RAM
buffer on every cycle. Holding preserves both the buffer and the evidence.

### 5.11 The diagnostic ladder

On any connect failure, run four rungs in order and record each with its latency. Each rung maps
to one call on the `Network` port (2.1), which is why that port exposes four calls rather than
one.

1. DNS. Resolve the broker hostname through `Network.resolve`. Failure classifies to
   `dns_nxdomain` or `dns_timeout`.
2. TCP. Connect to the broker port through `Network.tcp_connect`. A `tcp_refused` result means
   something answered and said no. A `tcp_timeout` result means a middlebox silently dropped the
   SYN, which is the signature of an egress filter.
3. TLS. Complete the handshake through `Network.tls_handshake`. A `tls_unknown_ca` result with a
   peer certificate whose issuer is not our CA means a TLS-inspecting middlebox is terminating
   the session. A `tls_notbefore` result means our clock, not our certificate. A `tls_expired`
   result means our certificate, not our clock. A `tls_hostname_mismatch` result means config.
   A `tls_handshake_timeout` result means interception without a valid substitute chain.
4. MQTT. Read CONNACK through `Network.mqtt_connect`. A `mqtt_not_authorized` result means the
   broker ACL refused our identity. A `mqtt_identifier_rejected` result points at the
   duplicate-client-id case.

The classifier stores the observed peer certificate issuer on a `tls_unknown_ca` result in the
`peer_issuer` field, because the issuer string names the middlebox vendor and turns a week of
argument into one screenshot.

Each classification maps to exactly one runbook signature (E48), so the ladder result is
directly actionable. 7.1 holds one unit test per classification value, each driven by a
`Network` fake configured to fail at that rung.

### 5.12 Fault injection and the ground-truth firewall

`FaultInjector` reads the materialised fault schedule that
`docs/design/variability-and-faults.md` C.2 defines, and never samples fault arrivals inside the
run loop. Activation publishes `iot.fault.injected.v1` with the exact sim instant and the
`detectable_from_sim_ts` the schedule computed.

The full field-realistic fault set, mapped both to the source's list and to the settled fault
catalog so the two documents use one vocabulary:

| Source phrase            | Modes in this section                                                                                                       | Catalog ids                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |

### 5.13 Health scoring and MTTD (component 3)

For each active failure mode `i` on a device, four numbers and a confidence:

`S_i` comes from `fleet/severity.yaml`, defaulting to the catalog's `severity`. `O_i` comes from
`fleet/occurrence_table.yaml`, a deterministic band lookup on the measured incident rate for
that mode on that device type over a trailing window. `D_i` comes from
`fleet/detection_table.yaml`, a band lookup on `MTTD_p90 / pf_interval` for the detector that
raised it. `RPN_i = S_i * O_i * D_i`, in the range 1 to 1000. `c_i` is the detector's confidence
in the interval (0, 1].

```
active = sorted(active_modes, key=lambda m: m.mode_id)      # D-03
health_score = 100 * PROD over active of (1 - min(1, RPN_i / 1000) * c_i)
```

The score is always recomputed from the sorted active set and is never updated incrementally.
Floating-point multiplication is not associative, so an unordered product would make the score
depend on iteration order and a set-backed `active_modes` would make it depend on hash
randomization, which D-03 forbids outright. `active_modes` is a list sorted by `mode_id`
ascending in the domain model, in `fleet.health.scored.v1`, and at the point of computation.

The product form satisfies the properties the fleet layer needs: bounded in [0, 100], monotone
non-increasing in each `RPN_i`, recoverable to within one unit in the last place when a mode
clears, and multiplicative so two independent problems compound rather than merely add.
INV-HS-1 through INV-HS-7 assert all of them, and two of those invariants are stated with the
tolerance that floating-point arithmetic actually supports rather than with the word "exactly".

Cold start is specified, because the score is needed at the moment it is least supported. At
t=0 of any run, no incident history and no MTTD distribution exist, yet 3.4's lifecycle
transitions read `health_score` immediately. The rule:

- `O_i` falls back to `fleet/occurrence_prior.yaml`, which holds one band per
  `(mode_id, device_type)` pair with a documented basis, until the trailing window holds at
  least `fleet.health.min_occurrence_observations` device-hours (default 168).
- `D_i` falls back to `fleet/detection_prior.yaml`, keyed on `(detector_id, mode_id)`, until at
  least `fleet.health.min_detection_events` matched detections exist (default 10).
- While either prior is in use, `c_i` is multiplied by `fleet.health.prior_confidence_penalty`
  (default 0.5), and `fleet.health.scored.v1` carries `prior_used` naming which of the two.
- The tables are computed within-run by default. `fleet.health.carry_history` (default false)
  carries them across runs, and config validation refuses it whenever the run is part of a hash
  comparison, because a carried table is state outside the seed.

INV-HS-7 asserts that a device with zero history has a defined `health_score` in [0, 100] and
that `prior_used` is populated, and S-IOT-16 asserts it end to end at t=0 across a whole fleet.

Two rating methods ship, selected by `fleet.fmea.method: rpn | action_priority`. The reason for
the second one is arithmetic and needs no citation: the product `S * O * D` maps 10 x 2 x 5 and
2 x 10 x 5 to the same 100, and a severity-10 mode is not the same risk as an occurrence-10 mode.
`test_rpn_collides_on_ordered_triples` enumerates the 1000 rating triples, reports how many
distinct triples share each RPN value, and is the demonstration rather than an assertion.

The Action Priority alternative is attributed rather than asserted. The AIAG and VDA FMEA
Handbook, first edition, 2019, is the reference commonly named for replacing the risk priority
number with an Action Priority lookup on the ordered triple (S, O, D) that yields High, Medium,
or Low. That handbook is a paid publication, the AIAG page for it returned HTTP 404 on
2026-08-09, and no copy of its table was retrieved for this spec, so the attribution is stated in
text and no published AP value is reproduced here. `fleet/ap_table.yaml` ships as a repo-defined
table with its own documented derivation rule, is labelled as repo-defined in the file header and
in every report that prints it, and is replaceable by an adopting organisation with its own
licensed copy. Open question 9.3 tracks whether the published table can be reproduced lawfully,
and until it is answered the repo makes no claim that its table matches the handbook's.

`MttdAccountant` pairs `iot.fault.injected.v1` with `fleet.fault.detected.v1` using a matching
window and a mode compatibility rule. The outcomes are true positive (latency recorded), miss
(an injection with no match by end of run, right-censored), and false positive (a detection with
no match). A detection earlier than `detectable_from_sim_ts` is recorded as leakage and fails
the run, per `docs/design/variability-and-faults.md` C.3.

`fleet.mttd.v1` always carries `detection_rate` and `censored_n` alongside `mttd_mean_s`.
Reporting a mean over detected faults only, without the detection rate, is the standard way this
metric lies, and INV-MTTD-1 asserts both fields are present and non-null in every emission. Mean
MTTD per fault class goes on an I-MR chart through the LSS engine; the distribution (p50, p90,
max) is what the runbook carries.

Degraded flagging follows 3.4: a threshold with a 5-point hysteresis band and a dwell time.

### 5.14 Predictive maintenance

Runs on any channel with a `degradation` block. The conveyor motor temperature, vibration, and
current channels are the phase-3 target named in the source.

1. Duty-cycle correction. Raw motor temperature is dominated by whether the motor is running.
   `DutyCycleRegression` fits an ordinary least squares model of the reading against a design
   matrix of twin-state indicators (running, idle, faulted, speed band, load band) and subtracts
   the fitted value, so the residual is the health signal rather than the schedule. Without this
   step the trend test measures shift patterns. This is the estimator VG-IOT-09 gates.
2. Feature extraction per window: mean, RMS, kurtosis, and crest factor for vibration; band
   energies at 1x, 2x, and 3x running speed and at the four bearing defect frequencies computed
   from the bearing geometry:

   ```
   FTF  = (fr/2) * (1 - (Bd/Pd) cos a)
   BPFO = (Nb/2) * fr * (1 - (Bd/Pd) cos a)
   BPFI = (Nb/2) * fr * (1 + (Bd/Pd) cos a)
   BSF  = (Pd/(2*Bd)) * fr * (1 - ((Bd/Pd) cos a)^2)
   ```

   with `Nb` ball count, `Bd` ball diameter, `Pd` pitch diameter, `a` contact angle, and `fr`
   shaft rate, all catalog fields on the attached bearing.

3. Trend detection with Mann-Kendall for the presence of a monotone trend. It is nonparametric,
   makes no distributional assumption, uses the exact null for small n, and uses the normal
   approximation with tie correction for large n. Theil-Sen supplies the slope and its
   confidence interval, and it resists the outliers vibration data always has.
   `OrdinaryLeastSquares` runs on the same series as the parametric comparator, and the bakeoff
   publishes both slopes so robustness is shown earning its place.
4. Time to threshold: `tt = (limit - level_now) / slope`, with the interval propagated from the
   Theil-Sen slope CI. Because the slope CI can straddle zero, the estimate is reported as an
   interval that can be unbounded, and the published event says so rather than printing a false
   point estimate. The demo sentence the source asks for becomes: "motor 2 bearing trend crosses
   the alarm limit in about 9 days, 95% interval 6 to 14 days."
5. EWMA on the duty-cycle-corrected residual for change detection on the same series, giving a
   second, faster detector with a different failure profile.
6. Escalation to Isolation Forest on the multivariate feature vector, then to a learned RUL
   regressor, each entered only if it beats the statistical baseline on the labelled synthetic
   incident corpus. The comparison table is published either way, per the locked decision.
   Scoring is on PR-AUC, MTTD p50 and p90, false alarms per device-week, and prognostic horizon
   (how early a true positive fires relative to the P-F interval).
7. Emission of `pdm.prediction.v1`, and when `tt` falls inside the maintenance planning horizon,
   `maintenance.workorder.requested.v1` with the runbook reference attached.

Every learned component is deterministic or it does not steer the run (D-04). The Isolation
Forest and the RUL regressor take `random_state` derived from the `model.train.<model_id>.seed`
stream in 5.29, run single-threaded with a pinned model artifact hash, and reach the run through
the kernel `Inference` port so simulation mode can bind a recorded-response adapter. A model
that cannot meet that contract becomes an advisory output written to the provenance sidecar and
does not enter the tape.

### 5.15 mTLS and device identity (component 6c)

An internal two-level CA. `twinflow-root-ca` is offline and long-lived and signs
`twinflow-device-ca` (which issues device certificates) and `twinflow-infra-ca` (broker and
gateway server certificates). A separate `twinflow-manufacturing-ca` signs birth credentials.

The operational device certificate profile:

- Subject `CN={device_id}`, SAN URI `urn:twinflow:device:{device_id}`.
- `basicConstraints: CA:FALSE`, `keyUsage: digitalSignature`, `extendedKeyUsage: clientAuth`.
- Validity 90 days, renewal at 60 days (2/3 of lifetime), with an overlap window in which both
  certificates validate.
- The key is generated on the device. The private key never crosses the network, at enrollment
  or at renewal. The device sends a CSR.

Broker ACL is derived from the certificate, not from IP and not from username. A client
authenticated as `CN=portal-dock3-a` may publish only under the Sparkplug identifiers and mirror
topics that resolve from that device's registered `UnsPath`, and may subscribe only to its own
NCMD and DCMD topics. The ACL file is generated from the registry, so it cannot drift from the
fleet. A test asserts that a client presenting device A's certificate is refused when publishing
to device B's topic.

Revocation uses a CRL published by the CA and reloaded by the broker on a schedule. The
revocation test revokes, reloads, and asserts the connection is refused.

The reason identity is certificate-based rather than IP-based or username-based is demonstrated
rather than argued: the `dhcp_lease_loss` fault changes a device's address mid-run, and the
certificate-based ACL is unaffected while an IP-based ACL would break. That is S-IOT-11, a
two-line chaos scenario that makes the design argument better than a paragraph would.

### 5.16 Edge tiers (E36)

| Tier | Location                                    | Runs                                                                                                                                      | Latency budget                            |
| ---- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 0    | on device                                   | deadband filtering, debounce, on-device RMS aggregation, threshold alarms                                                                 | 10 ms                                     |
| 1    | gateway per area (NanoMQ + `twinflow-edge`) | protocol translation, store-and-forward, aggregation, local inference (EWMA residual, safety interlocks), UNS bridging, later the E32 SLM | safety interlock 100 ms, anomaly flag 1 s |
| 2    | site (EMQX, historian, twin sync)           | historian writes, twin recalibration, SPC evaluation, UNS mirror publication                                                              | 10 s                                      |
| 3    | network (planning, MEIO, hosted LLM)        | forecasting, optimisation, agent                                                                                                          | no budget                                 |

The 100 ms and 1 s numbers are the source's own and are config keys (`edge.latency_budget_ms`).
Two different things are checked against them, and conflating them would produce a gate that
cannot fail.

The simulation-mode check is a model consistency check, named IC-IOT-05, not a performance gate.
In simulation mode the latency of a decision is the sum of the modelled stage costs the config
supplies, so comparing it against a budget from the same config proves only that the arithmetic
is right. IC-IOT-05 asserts exactly that and no more: the modelled p99 for each function class
equals the sum of its declared stage costs to within 1e-9, and `edge.tier.decision.v1` carries
`latency_source: model`. What would falsify it is a placement table whose declared stage costs
do not add up to the latency the model reports, which is a real defect and a real failure mode
of a hand-maintained placement table.

The performance gate is BM-IOT-01, and it measures. It runs the actual tier-0 and tier-1 code
paths, with no simulated stage costs, over a fixed workload of 10,000 samples per function
class, on stated hardware named in the artifact. It writes `artifacts/edge/bench_{date}.json`
with the p50, p95, and p99 per function class, the hardware description, the git SHA, and the
dependency lockfile hash, the same way 5.26 commits the HIL self-test. It fails when a p99
exceeds its budget on the reference runner, and it reports rather than fails on any other
runner, because a loaded shared runner cannot falsify a latency claim. The committed artifact is
what the README cites.

BM-IOT-01 reads a real monotonic clock, and D-02 permits that only because the benchmark harness
is not the simulation. The harness runs outside any run, its readings never enter an event
payload or the hashed tape, and no simulation control decision consults them. The one crossing
point is `edge.tier.decision.v1`, which carries `latency_source: model` inside a run and
`latency_source: benchmark` only in the artifact the harness writes, never in a recorded run's
event stream. `test_benchmark_timings_never_enter_the_tape` runs the determinism scenario with
the benchmark harness enabled and disabled and asserts the two event-log hashes are equal.

The production-mode number is evidence, not a gate. OpenTelemetry spans in production mode
produce the same three percentiles, and `just edge-report` writes them to
`artifacts/edge/otel_{date}.json` with the deployment described. `edge.tier.decision.v1` carries
`latency_source: benchmark` for those.

`facility.yaml` carries an `edge.placement` table assigning every function to a tier with a
written rationale. `PlacementReport` renders it to `artifacts/edge/placement_report.md`.

E36 asks for the compute-placement table to sit in ARCHITECTURE.md beside the ISA-95 map, so it
does. ARCHITECTURE.md carries the table between two marker comments, `just edge-report`
regenerates the block from `artifacts/edge/placement_report.md`, and
`test_architecture_placement_block_is_current` asserts the sha256 of the block in
ARCHITECTURE.md equals the sha256 of the generated report. Generating the artifact is the better
engineering choice and transcluding it into ARCHITECTURE.md is what the requirement asks for;
doing both, with a checksum test, is the way to have neither drift.

### 5.17 Measured edge economics

Three quantities, and each one states whether it is measured or computed, because two of them
were presented as measurements when they are arithmetic.

Bandwidth has a measured half and a computed half. The measured half is `wire_bytes`: the actual
serialized length of every Sparkplug frame `LinkAccountant` sees crossing a tier boundary,
summed per window, plus `raw_wire_bytes_equivalent`, which is the actual serialized length of
the same window's records encoded one per frame with no deadband and no aggregation. Both
numbers come from the codec, both are bytes a packet capture would agree with, and their ratio
is the compression ratio the README cites. The computed half is `deadband_suppressed` and
`aggregation_reduced`, which are counts derived from the same config that produced the
filtering; they explain the ratio and they are labelled as bookkeeping, not as measurement.
BM-IOT-02 is the gate over the measured half, and it fails when the wire-byte total disagrees
with the sum of the frame lengths the transport adapter recorded.

`bytes_per_finding` divides `wire_bytes` crossing tier 1 to tier 2 by the findings produced from
that window. It is a ratio of two measured counts.

Latency reports p50, p95, and p99 per function class per tier, from IC-IOT-05 in simulation mode
and from BM-IOT-01 and the production OpenTelemetry spans as evidence, exactly as 5.16 splits
them.

Degradation is exercised, not described. The `gateway_partition` scenario cuts tier 1 from tier
2 and produces `edge.degraded.v1` listing retained capabilities (safety interlocks, local
anomaly flagging, local buffering, the line keeps running) and lost capabilities (SPC
evaluation, twin sync, agent answers, cross-area correlation). `DegradationReport` generates the
lists from the placement table rather than from prose, so they stay true as the system grows.

The tier-0 deadband and tier-1 aggregation policies are the levers. Raw high-rate vibration is
retained locally in a ring for `local_retention_hours`, only window statistics cross the
boundary, and the raw window is fetchable on demand when a finding needs it. That is what real
historians do and it is why the bandwidth number is large. S-IOT-13 measures the suppression
rate and the wire-byte ratio on a fixed workload and writes both to the artifact.

### 5.18 Zero-touch provisioning (E44)

1. The device boots with a birth credential in NVS: an X.509 certificate signed by
   `twinflow-manufacturing-ca` with `CN={serial}`. For the ESP32 this is written at flash time
   by `just hil-flash`.
2. The time gate passes.
3. The device connects to the provisioning endpoint over mTLS presenting the birth certificate.
4. `ProvisioningAuthority` checks that the chain validates to the manufacturing CA, that
   `serial` is on `fleet/allowlist.yaml`, that the serial is not already enrolled with a
   different key, that the enrollment nonce is unused, and that the birth certificate is not
   revoked.
5. The device generates a keypair locally and sends a CSR.
6. The authority issues the operational certificate, assigns a `UnsPath` and an `edge_node_id`
   from `fleet/placement_policy.yaml` (a rule set mapping serial ranges and device types to
   areas and lines), and returns the desired config document.
7. The device stores the certificate and config in NVS, reconnects to the operational broker,
   and publishes NBIRTH.
8. The registry publishes `fleet.device.enrolled.v1`. Zero human steps.

Every rejection path publishes `fleet.enrollment.rejected.v1` with a distinct `reason` value and
a distinct runbook reference: `serial_not_allowlisted`, `nonce_reused`, `birth_cert_revoked`,
`serial_key_mismatch` (a cloned device), and `clock_outside_gate`. The enrollment nonce draws
from the `fleet.provisioning.nonce` stream (5.29), so a replayed run reproduces the same nonces
and the `nonce_reused` path is reproducible rather than incidental.

### 5.19 Desired versus reported reconciliation (E44)

The reconciler runs on every DBIRTH and on `fleet.reconcile_interval_s`. It diffs `desired`
against `reported` by JSON pointer, producing `DriftItem` records sorted by path. Each item is
aged, and items older than `fleet.drift.grace_s` become `fleet.compliance.violation.v1` findings.

Four actions:

`push` is the default. It resends the desired document, increments `desired_version`, and waits
for the echo.

`accept` adopts the reported value as desired. It needs an authority tier and is written to the
decision register. Both exist before reconciliation is built: `AuthorityTier` lands in
`twinflow-contracts` at P1 with E5a's autonomy metadata, the append-only decision register lands
at the ECON phase with E21a, and E44's reconciler lands at P6-W1 after both. Config validation
refuses `accept` in any compliance policy while either is absent, and the reconciler treats a
policy that names it as a load error, so the action is never silently unavailable at runtime.
Section 8 holds the phase trace.

`quarantine` applies to paths flagged `security_critical` in the compliance policy: the
certificate fingerprint, the broker host, and the firmware hash.

`unreconcilable` applies after `max_push_attempts`. It stops pushing and raises a severity-8
finding. Pushing forever against a device that cannot apply the config is a loop that hides the
problem.

INV-DRIFT-1: reconciliation is convergent. Under repeated push with no external change, the
drift item count is non-increasing and reaches either zero or a stable `unreconcilable` set.

### 5.20 OTA campaigns (E44)

```
Campaign := {
  campaign_id, target_firmware {version, sha256, signature},
  selector,                      # device query: type, area, current version, health floor
  rings: [Ring],
  health_gate, rollback_policy,
  created_by, authority_tier
}
Ring := {name, size_pct | device_ids, soak_duration_s, promote_criteria}
```

Default rings: `canary` (1 device or 2%, whichever is larger), `early` (10%), `broad` (50%),
`fleet` (100%).

Transfer is chunked with a per-chunk sha256 and a resume offset persisted in NVS, so a device
that loses the link mid-download resumes rather than restarting. The signature is checked over
the whole image before it is written to the inactive slot.

Apply writes to the inactive slot (A/B partitions), sets the boot partition, and reboots. The
new image boots with `ota_pending_verify = true`. It must reach `ONLINE`, publish NBIRTH, and
stay online for `verify_soak_s` before the agent marks the image valid. If it does not, the
bootloader rolls back to the previous slot on the next boot. This is the ESP-IDF rollback
mechanism and it is what makes a botched push survivable without a truck roll.

The promotion gate promotes a ring only if, over the soak window, the paired before-and-after
comparison of ring device health shows no regression beyond tolerance, the `crash_loop_count`
delta is zero, and the publish-rate ratio is within `publish_rate_tolerance`. The health
comparison is a paired statistical test, and 5.30 defines how the campaign engine gets one
without importing the LSS engine. `ota.ring.gate.evaluated.v1` carries the statistic, the
p-value, and the effect size. The promote decision is a test result, not a threshold on an
eyeballed dashboard.

Rollback is automatic on gate failure. The campaign halts, the ring rolls back, and
`ota.campaign.halted.v1` names the failing criterion.

KPIs: the adoption curve (percent on target version against sim-time), per-ring failure rate,
time-to-fleet-consistency, rollback count, bytes transferred, and bytes transferred per
successfully updated device, which exposes the cost of retries.

INV-OTA-1: at every instant, every device's active firmware is either the campaign target or a
version in the campaign's declared rollback set, never an unknown version.

INV-OTA-2: a device is in at most one active campaign.

### 5.21 RF link budget (E46)

Forward link (reader to tag), the one that usually limits:

```
P_tag(dBm) = P_tx + G_ant(theta, phi) - L_cable + G_tag(theta_t, phi_t)
             - PL(d) - L_pol - L_occlusion + fading
```

The tag activates when `P_tag >= tag.sensitivity_dbm`. Reverse link (tag backscatter to reader):

```
P_rx(dBm) = P_tag - L_backscatter + G_tag + G_ant - L_cable - PL(d) + fading
```

A read succeeds on a round when both margins are non-negative and the round is not lost to
collision.

Path loss uses an exponent model `PL(d) = PL(d0) + 10 n log10(d/d0)`, with `n = 2` reducing to
free space. The free-space case is checked against the closed form (IC-IOT-02), which is an
internal consistency check and is listed as one, because a model compared with its own analytic
solution is not external validation. A rack aisle uses `n` in the 2.5 to 3.5 range from config,
and the configured `n` carries the source string
`"repo-defined modelling assumption, not a measurement"`.

`L_pol` is 3 dB for a circularly polarized reader antenna against a linearly polarized tag, and
`-20 log10(abs(cos(psi)))` for linear against linear at relative angle `psi`, saturating at
`pol_null_floor_db` so a perfect null does not produce infinity. The 3 dB figure is the
polarization loss factor of 0.5 that Balanis gives for a circularly polarized wave incident on a
linearly polarized antenna, in "Antenna Theory: Analysis and Design", 4th edition, 2016, section
2.12. That text is a paid book and was not retrieved for this spec, so the citation is carried
at single-source confidence with the attribution stated in text, and VG-IOT-15 checks the two
limiting cases against it rather than against hand arithmetic.

`L_occlusion` comes from `TagPose.occluding_material` and `depth_in_pallet`. The shipped
defaults are `none: 0.0`, `cardboard: 0.5`, `liquid: 6.0`, and `metal: 20.0` dB per layer, and
every one of them carries the source string
`"repo-defined modelling assumption, not a measurement"`, because no published measurement
series for these materials at 900 MHz was retrieved for this spec. Open question 9.15 tracks
replacing them with measured values and naming the source. What the model does claim is
ordering, not magnitude: INV-RF-7 asserts `none < cardboard < liquid < metal` and that read rate
falls monotonically in `depth_in_pallet`, which is the part a reader can believe and the part
a test can prove. A pallet of bottled product reading worse than a pallet of empty totes is an
ordering claim, and ordering is what is asserted.

Fading is a Rician draw per inventory round, with the K factor from config. Redrawing per round
is what makes multiple rounds help, which is the physical reason dwell time matters.

### 5.22 Read probability

For a tag passing a portal:

```
dwell_s   = zone_length_m / pallet_speed_mps
rounds    = floor(dwell_s * effective_round_rate_hz)
p_round   = P(both margins >= 0 under the fading draw)
p_read    = 1 - (1 - p_round) ** rounds
```

`effective_round_rate_hz` is reduced by singulation collision. The singulation model implements
the slot counter the EPC Gen2 air interface defines, so its parameters are the specification's
parameters and not invented ones.

The primary text is the GS1 EPC Radio-Frequency Identity Generation-2 UHF RFID Standard, Release
3.0.1, Ratified, February 2026, retrieved 2026-08-09 from <https://ref.gs1.org/standards/gen2/>,
HTTP 200. Three facts from it fix the model. Annex J.1 states that each tag carries a 15-bit slot
counter, that on a Query or QueryAdjust a tag loads a value between 0 and `2^Q - 1` drawn from
the tag's own random number generator, and that Q is an integer in the range 0 to 15. Clause
6.3.2.10 repeats the same range rule at each Query variant. Annex D, Figure D-1, gives the
interrogator-side adaptation loop as informative guidance: start at `Qfp = 4.0`, issue
`Query(round(Qfp))`, then set `Qfp = max(0, Qfp - delta)` on zero replies, leave `Qfp` unchanged
on exactly one reply, and set `Qfp = min(15, Qfp + delta)` on more than one reply, with typical
`delta` in the open interval 0.1 to 0.5 and smaller `delta` at larger Q.

The frame is `2^Q` slots, never an arbitrary integer, which is why this section says
"one Q step" rather than "a factor of two" and means the same thing. With `T` tags in the zone
the expected slots per successful singulation grows with `T`, so the per-tag round rate falls
roughly as `1/T` once `T` exceeds `2^Q`. That is the reason a 40-case pallet reads worse than a
5-case pallet at the same speed, and it is the effect most read-rate models omit.

The claim carries two gates because it has two halves and they have different evidence.

VG-IOT-11 covers the half with primary text. It drives the implemented interrogator adaptation
loop against the Annex D transition rules over a scripted reply sequence and asserts the Q
trajectory matches the figure exactly, that `Q = round(Qfp)` is clamped to 0 through 15, and that
a tag's loaded slot value never leaves 0 through `2^Q - 1` over 10^6 seeded draws. It is
falsified by any Q outside the range, any slot value outside the range, or any transition that
moves Q in the direction the figure does not name.

VG-IOT-12 covers the half whose reference is blocked. Schoute reports the maximum normalized
throughput of framed slotted ALOHA as `1/e`, about 0.368, attained when the frame size equals the
number of contending tags, in "Dynamic Frame Length ALOHA", IEEE Transactions on Communications,
volume 31, number 4, 1983, pages 565 to 568. The paper is behind a publisher paywall and the DOI
resolver returned HTTP 202 with an empty body on 2026-08-09, so the citation is carried at
single-source confidence with the attribution stated in text. The gate sweeps Q from 0 to 9,
which is frame sizes 1 to 512, at tag counts 1 to 512, and requires a maximum normalized
throughput within 0.010 of 0.368 attained at a Q whose `2^Q` is within one Q step of the tag
count. The noise floor is measured, not assumed: the same sweep runs at 200 replications, the
standard error of the maximum is written to the artifact, and the gate fails its own
preconditions if that standard error exceeds 0.010. What falsifies the gate is a measured maximum
outside 0.358 to 0.378, or a maximum attained more than one Q step from the tag count, either of
which means the slot-selection model is wrong. INV-RF-4 (monotone in tag count) remains, and it
is a sanity property rather than the evidence for this claim.

Interference reduces `p_round` two ways. A raised noise floor from local drives lifts the
required receive margin. Reader-to-reader interference applies when two portals' zones overlap
in time and frequency, and `dense_reader_mode` mitigates it. The model represents dense-reader
mode as a round-rate reduction rather than a probability reduction, because dense-reader time
and frequency division costs rounds.

Miss cause attribution records the binding constraint when a pass produces no read. `MissCause`
is chosen by which term of the budget failed first: `OUT_OF_RANGE`, `ORIENTATION_NULL`,
`OCCLUSION`, `COLLISION`, `SPEED`, or `INTERFERENCE`. Without the cause, "4% missed" is a
number. With it, it is a fix.

### 5.23 Cross-reads

A cross-read is a tag physically at portal A that is read by portal B. It is generated from the
geometry: for every tag pose, the model evaluates `p_read` against every portal whose read
volume contains the pose, not only the intended one. `iot.rfid.read.v1` carries the reading
portal, and `iot.rfid.read.groundtruth.v1` carries the true portal and the `is_cross_read` flag.

Cross-reads are a false-positive class, not a duplicate class, and deduplication cannot fix them
because the read is genuine and simply attributed to the wrong location. The modelled
mitigations are all available as what-ifs: lower transmit power, re-aim the antenna, add
shielding between adjacent doors, or gate acceptance on a presence signal such as a photo-eye or
the `trailer_presence_loop` channel so reads are accepted only while a pallet is physically in
the zone. The last one is the fix that works in the field, and having it in the model means the
what-if can prove it.

### 5.24 Antenna placement as a what-if

`PlacementProblem` exposes antenna position, boresight azimuth and elevation, transmit power,
and conveyor speed as a search space, with regulatory ceilings as hard constraints. The
objective is multi-objective: maximise read rate, minimise cross-read rate, minimise throughput
cost from slowing the line, subject to a cost budget for added antennas.

The search is seeded (D-04). The sampler takes its seed from the
`search.placement.<portal_id>.sampler` stream in 5.29, runs with a fixed number of workers, and
is bounded by a deterministic trial budget rather than by wall-clock seconds. Without that,
`whatif.rf.reaim_antenna` would return a different answer every run and S-IOT-06's
statistically-significant-delta assertion would be flaky. `iot.rf.placement.evaluated.v1`
carries `search_stream_name` so the search that produced a candidate is reproducible from the
log alone.

The what-if surface the agent calls:

- `whatif.rf.add_antenna(portal_id, position, boresight, power)`
- `whatif.rf.reaim_antenna(antenna_id, azimuth, elevation)`
- `whatif.rf.set_power(antenna_id, dbm)`
- `whatif.rf.set_conveyor_speed(line_id, mps)`

Each returns read-rate delta, cross-read delta, downstream throughput delta from the twin, and
cost, with a hypothesis test on the before-and-after read-rate samples obtained through the seam
in 5.30. This is the source's own example, "dock 3 misses 4% of reads: add an antenna, re-aim
the existing one, or slow the conveyor", answered with numbers.

### 5.25 Physics problem versus device problem

The diagnosis the source names as the field skill. Read rate by portal goes on a p-chart, which
is the correct chart for a proportion and is chosen by the LSS engine's data-type selector. When
a portal drops below its LCL, the classifier decides between two causes:

| Signal                                          | Physics problem                              | Device problem                         |
| ----------------------------------------------- | -------------------------------------------- | -------------------------------------- |
| Read rate conditioned on tag orientation        | drops only in specific orientation bands     | drops uniformly                        |
| RSSI distribution of successful reads           | shifts (the marginal tags are the ones lost) | unchanged (fewer reads, same strength) |
| Per-antenna-port read share                     | shifts toward one port                       | uniform decline across ports           |
| Antenna VSWR channel                            | unchanged                                    | rising (cable or connector)            |
| Correlation with pallet build or conveyor speed | strong                                       | none                                   |
| Reader temperature, reboot count                | unchanged                                    | elevated                               |
| Neighbouring portal read rates                  | may rise (cross-reads absorbed)              | unchanged                              |

The classifier is a documented decision rule over those seven signals, published as code in
`twinflow.rf.diagnose`, with its outputs scored against the ground-truth fault injections.
Shipping the rule and its measured accuracy is the differentiator; asserting that the diagnosis
is possible would not be.

Adding `antenna_vswr` as a first-class channel on the portal reader type is what makes the
fourth row possible. Real readers report per-port return loss, and a rising VSWR is a cable or
connector problem, not an RF-environment problem.

### 5.26 Hardware in the loop (E47)

The physical device is the same Rust crate built with `--features esp32`. It enrolls through the
ZTP flow in 5.18, publishes into the same UNS beside the simulated peers, receives OTA campaigns
from the same engine, and appears on the dashboard with a `physical: true` badge and no other
difference.

Four rules make this honest.

1. HIL forces production mode. A physical device cannot obey a virtual clock. `hil.enabled:
   true` implies `mode: production`, and the run manifest records `deterministic: false`. No
   eval, no README number, and no golden file may come from a HIL run. This is stated in the run
   manifest so it cannot be forgotten.
2. The physical device publishes only. Its inbound command surface is restricted to
   `Node Control/Rebirth` and OTA. It actuates nothing. A test asserts that any other DCMD to a
   device with `physical: true` is refused at the gateway.
3. CI cannot prove the hardware path. A nightly job builds the `esp32` target and boots it under
   the Espressif QEMU fork, asserting it reaches `TIME_SYNC_WAIT` and publishes a valid boot
   record. That proves the build and the early state machine, not the radio. The full hardware
   self-test (`just hil-selftest`) is run by a human against real hardware, and its output, with
   the date, the firmware hash, and the git SHA, is committed to `artifacts/hil/`. The README
   says exactly this. Claiming CI coverage of a physical device would be the kind of overclaim
   the rest of the repo exists to avoid.
4. The time gate earns its keep here. A real ESP32 with no RTC boots at 1970, and the gate is
   what turns that from a confusing TLS failure into a logged, expected `TIME_SYNC_WAIT`.

The CI cost of the `esp32` target is priced in section 8 rather than assumed, because the
esp-idf toolchain is not free to provision on a hosted runner.

### 5.27 Runbook generation (E48)

A failure signature is `sha256(mode_id, device_type, detector_id)`, truncated. On the first
occurrence of a signature the generator publishes a runbook. On later occurrences it updates the
statistics and bumps the version only when the change is material, where material is decided by
a hypothesis test on the MTTD shift rather than by any change at all.

Fields are composed from four sources. The symptom comes from the catalog's
`detection_signature`, rendered with the observed evidence window. The root cause comes from the
ground-truth fault mode, which only the simulation knows, and that is the single reason these
runbooks are better than hand-written ones: the root cause is recorded, not inferred. The fix
and prevent sections come from a per-mode template in `catalog/runbook_templates/{mode_id}.md`,
filled with device and config specifics. MTTD, S, O, D, RPN, and Action Priority come from the
fleet layer.

Output is `artifacts/runbooks/{signature_id}.md` in the author's field format (Symptom, Root
cause, Fix, Prevent, MTTD, S-O-D and RPN), plus a record in the CMMS analog, plus
`fleet.runbook.published.v1`. The agent cites the runbook by `signature_id` when the failure
recurs, which makes it a valid grounding source under E26(f).

The coverage test is the one that keeps the library complete as the catalog grows: for every
failure mode declared anywhere in the catalog, injecting it produces exactly one runbook with
all required sections non-empty. A new catalog entry with a new mode and no template fails CI.

discovering afterward that 300 devices now alarm is a known way to cause an alarm flood, and the

Renaming a stream is not a free edit and is not silently forbidden either. A.3 fixes the

recorded runs no longer reproduce. That is what makes an unavoidable break loud and dated rather
than a silent hash change.

### 5.30 The statistical test seam

Two places in this section need a hypothesis test: the OTA promotion gate in 5.20 and the RF
what-if delta in 5.24. Neither `twinflow-fleet` nor `twinflow-rf` may import the LSS engine,
because the LSS engine is not in this section's DAG and pulling it in would put a statistics
stack inside the fleet server and inside the RF model.

The seam is an event round trip, which is what the locked architecture constraint asks for.

The requester publishes `ota.ring.gate.requested.v1` or `rf.whatif.evaluated.v1` on the
`EventBus` port (D-08), carrying a `request_id`, the metric name, and two sample references
resolvable in the historian. The LSS engine replies with `lss.test.completed.v1` carrying the
same `request_id`, the chosen test, the statistic, the p-value, the effect size, and the
assumption-check trace that chose the test. The requester correlates by `request_id` and writes
the result into `ota.ring.gate.evaluated.v1`.

Three behaviours make the seam safe rather than merely decoupled.

The reply has a deadline. `fleet.stats.reply_timeout_s` (default 300 sim-seconds) bounds the
wait. On timeout the campaign engine halts the ring and publishes `ota.campaign.halted.v1` with
`reason: stats_timeout`. It never promotes on a missing test, because promoting on a missing
test is exactly the eyeballed-dashboard behaviour the gate exists to replace.

The reply is part of the tape. Both events carry the D-07 envelope and both are ordered by the
canonical total order, so a replay reproduces the decision rather than recomputing it (D-04).

The contract is tested from both sides. C3's producer and consumer contract tests cover
`ota.ring.gate.requested.v1` here and `lss.test.completed.v1` in the LSS engine section, and
`test_fleet_imports_no_lss_module` asserts the import never appears.

because those five are the fields downstream contracts bind to. The merged document is what
`DeviceSpec` carries into the run (3.3), and the merge is applied at load so a validation error
names the line in the file the operator wrote rather than a line in the catalog.

`stampede_ceiling_per_100ms` is `null` by default so the derived value in 5.8 is used and stays
consistent with `broker.max_inflight`. Setting it to an integer overrides the derivation, and
setting it above `broker.max_inflight` is a config error, because a ceiling the broker cannot
honour is not a ceiling.

`fault_reset_reasons` names members of the `ResetReason` enum from 5.9. Validation refuses any
value that is not one of the sixteen, which is how a typo in a config file is caught rather than
silently narrowing the crash-loop detector.

```yaml

    "0": { latency_budget_ms: 10 }
```

`stage_costs_ms` is the list IC-IOT-05 sums. Declaring it in config rather than deriving it in

different budgets at that tier, 100 ms for safety interlocks and 1 s for anomaly flagging, and
collapsing them to one number would lose the requirement.

### 6.13 Cross-file validation rules

Beyond per-field types, the loader enforces the following, and each rule names the invariant or
test that also asserts it at runtime.

1. Every `devices.instances[].type_id` resolves in the catalog, and every `edge_node_id` on an
   instance resolves in `devices.edge_nodes` (INV-SPB-2).
2. Every `edge_nodes[].devices[]` id resolves in `devices.instances`, and the two directions
   agree, so a device cannot be hosted by a node that does not list it.
3. No two edge nodes share an `edge_node_id`, and no two agent processes claim one (INV-SPB-1).
4. Every `(attaches_to, uns_parameter)` pair across the bound fleet is unique, so no two channels
   collide on a UNS topic (INV-UNS-1).
5. Every `attaches_to` selector resolves to at least one resource in each of the three worked
   profiles from A2 (INV-CAT-5).
6. Every `capability_unlocks` id resolves in `catalog/capabilities.yaml`, and every capability
   there names a `realised_by` module or a `proven_by` test (INV-CAT-4).
7. Every `failure_modes[].catalog_id` resolves in `docs/design/variability-and-faults.md` C.4 or
   C.5, and every C.4 id this section owns appears in the 5.12 mapping (INV-CAT-6).
8. Every `signal_model.kind` resolves in the plugin registry, and the set of distinct kinds across
   the shipped catalog has cardinality at most twelve (INV-CAT-3).
9. Every `unit` resolves in the UCUM edition named in `catalog/UCUM_VERSION` (VG-IOT-05).
10. `warn_limit < alarm_limit < trip_limit`, all inside `range`, on every channel that declares
    them, and every channel with numeric limits carries a `limit_source`.
11. `fleet.health.recovered_above == fleet.health.degraded_below + fleet.health.hysteresis_band`,
    and `fleet.health.failed_below < fleet.health.degraded_below`.
12. Every `transport.qos_by_topic_class` entry matches its `conformance.yaml` row, or names a
    departure rule id in `transport.conformance_departures` (INV-QOS-1), and every
    `conformance.yaml` row with a null `rule_id` carries a written basis (INV-QOS-2).
13. `edge.placement[].tier` is at most the tier of the gateway serving the device, and every
    function's `stage_costs_ms` sums to at most its `latency_budget_ms` (IC-IOT-05).
14. `rf.regulatory` radiated power is within the ceiling for the declared `(region, band)` pair,
    and the antenna beam-width satisfies the coupling in 3.7 (VG-IOT-04).
15. `rf.singulation.q_max <= 15` and `rf.singulation.slot_counter_bits == 15`.
16. `deployment.adapters` is absent whenever `simulation.mode` is `simulation` (D-12).
17. `security.epoch_floor: build_timestamp` and `hil.enabled: true` each need
    `simulation.mode: production`.
18. `pdm.window.stride_s` divides `pdm.window.length_s`, and
    `pdm.learned.inference_port` is `recorded` whenever `simulation.mode` is `simulation` (D-04).
19. `pdm.learned.model_artifact_hash` is non-null whenever a learned detector appears in
    `pdm.bakeoff.detectors` and the run is not a bakeoff-only run.
20. `ota.campaign_defaults.rings` is non-empty, ring `size_pct` values are non-decreasing, and
    the last ring is 100.
21. Every path in `fleet.drift.security_critical_paths` is a valid RFC 6901 JSON pointer and
    resolves in the desired config document of at least one device type.
22. `transport.broker.keepalive_s` satisfies every `value_range` rule in `fleet/policy.yaml` that
    applies to `/transport/keepalive_s`, so the shipped default cannot raise a violation against
    the shipped policy.

Rules 11, 12, 16, 17, 18, and 22 are the ones that exist because the alternative is a run that
starts and then behaves wrongly. The rest are the ordinary kind that catch a typo.

### 6.14 Error reporting (C5)

Config is parsed with `ruamel.yaml` in round-trip mode so every node keeps its line and column,
which is why 2.3 lists `ruamel.yaml` as a dependency of `twinflow-sensors` rather than a plain
YAML loader. Errors are formatted with the file, the line, the column, the offending value, the
valid set, a suggestion, and a documentation link:

```
catalog/sensors/warehouse_logistics.yaml:214:11: error: channels[1].signal_model.kind:
    "rf_readzone" is not a registered signal model kind
    registered kinds: steady_state, first_order_lag, duty_cycled,
        rotating_machine_vibration, counter, event_stream, rf_read_zone, positional,
        binary_state, electrochemical, level_gauge, load_bridge
    did you mean: rf_read_zone
    see: docs/CONFIGURING.md#signal-models

facility.yaml:88:7: error: fleet.health.recovered_above: 72.0 does not equal
    fleet.health.degraded_below (70.0) plus fleet.health.hysteresis_band (5.0)
    the hysteresis band in section 3.4 is what stops lifecycle flapping
    set recovered_above to 75.0, or change hysteresis_band to 2.0
    see: docs/CONFIGURING.md#fleet-health

facility.yaml:12:3: error: deployment.adapters is not permitted when simulation.mode is
    "simulation"
    the simulation port family has no adapter choice to make (doctrine D-12)
    remove the block, or set simulation.mode to "production"
    see: docs/design/DOCTRINE.md#d-12
```

Suggestions come from `difflib.get_close_matches` over the valid key or value set. All errors in
a file are collected and reported together, never one per run. `twinflow-fleet validate-config`
exits non-zero on any error and is wired into `just validate` and the pre-commit hook. A
`--dry-run` mode loads every config, binds every device, resolves every `attaches_to` selector,
builds every Sparkplug alias table, and reports what would run without opening a socket or
touching the historian, which is what makes `just run --dry-run` able to name an unresolved
selector before a run rather than during one.

## 7. Testing

Five tiers with runtime budgets (C4), plus two benchmark jobs that measure rather than assert.
All tiers run on `just test`; CI runs them as separate path-filtered jobs (C10). Every test in
this section states the observation that would fail it, per D-12, and a test whose failure
condition cannot be described does not appear here.

### 7.1 Unit tests (budget: 90 s)

Per-function tests over hand-computed fixtures. The ones that are easy to get wrong are named here rather than left to a coverage number:

- One test per `classification` value in `iot.device.diag.ladder.v1`, thirteen failure values plus
  `ok`, each driven by a `Network` fake configured to fail at exactly one rung (5.11). The fake
  fails at the rung, not at the call, which is why the port exposes `resolve`, `tcp_connect`,
  `tls_handshake`, and `mqtt_connect` separately (2.1).
- `peer_issuer` is populated on `tls_unknown_ca` and absent on every other classification.
- Sparkplug alias assignment: a metric absent from DBIRTH raises at encode time rather than
  publishing an invalid stream, and the raised message names the metric and the DBIRTH.
- `seq` wraps 255 to 0 and never skips; NBIRTH carries `seq = 0`; a rebirth resets `seq` to 0 and
  keeps `bdSeq`.
- `bdSeq` increments in NVS across a simulated reboot, and the NDEATH will registered at CONNECT
  carries the same value the following NBIRTH carries.
- `UnsPath` construction refuses a segment containing `/`, `+`, `#`, or an uppercase letter, and
  the error names the offending segment.
- `UnsPath.from_resource` and `to_resource` on a five-segment resource path, where the two deepest
  segments join with a dot into the Sparkplug metric name.
- Full-jitter delay is drawn from the `device.backoff.<device_id>.jitter` stream and lands in
  `[0, min(cap_ms, base_ms * 2 ** attempt_index)]` at every `attempt_index` from 0 to 20.
- The retry index resets after `stability_s` online and not on CONNACK alone; the test drives a
  broker that accepts and drops after 1 s and asserts the delay keeps growing.
- Time gate: no TLS handshake and no token mint below `security.epoch_floor`, and the ceiling
  refuses a clock beyond `epoch_ceiling_years`.
- `StoreAndForward` drop policy: `oldest` and `newest` each drop exactly the record the policy
  names, and `dropped_records_total` increments by exactly one per drop.
- Deadband: a suppressed sample increments `deadbanded`, is written to the ground-truth stream,
  and is published anyway once `max_publish_interval_s` elapses.
- Health score on a hand-computed two-mode case, checked against the product form to 1e-12
  relative, and the same case with the modes supplied in the other order, checked for exact
  equality after sorting.
- Occurrence and detection band lookup at every band boundary, including both open ends.
- Cold start: a device with no history yields a defined score and a populated `prior_used`.
- `MttdAccountant` on a constructed pairing set containing one true positive, one false positive,
  one miss, and one detection earlier than `detectable_from_sim_ts`, asserting the last one is
  recorded as leakage and fails the run.
- Bearing defect frequencies on a hand-computed geometry, including the identity
  `BPFO == Nb * FTF`, which holds for any geometry and is the cheapest arithmetic check on the
  four formulas.
- `TimeToThreshold` returns an unbounded interval exactly when the Theil-Sen slope confidence
  interval straddles zero, and the event says so rather than printing a point estimate.
- `MissCause` selection: six constructed passes, one per cause, each failing exactly one budget
  term first.
- Config error formatting: file, line, column, offending value, valid set, suggestion, and
  documentation link all present, on one example per rule class in 6.13.

### 7.2 Property-based invariants (Hypothesis, budget: 240 s)

Fifty-three named invariants, each a `@given` test running under a seeded `derandomize` profile
in CI so a failure is reproducible from the printed seed alone.

| Id          | Invariant                                                                                                                                                                                                                                  |

### 7.3 Seeded end-to-end scenarios (budget: 900 s)

Seventeen scenarios, each running in simulation mode at a fixed seed and asserting an outcome
chain rather than a single number.

**S-IOT-01, kill the broker and lose nothing.** Run a 200-device fleet, kill the broker for 20
simulated minutes, restart it. Assert: every node moves `ONLINE` to `BUFFERING`; buffered bytes
stay under `cap_bytes`; no record is dropped because the outage fits the buffer; replay is paced
at `replay_rate_msgs_s`; `INV-SF-1` balances at every instant; the historian holds the same record
count as the ground-truth stream; and the reconnect histogram satisfies INV-BO-2. This is
the demo component 6c asks for, and the assertion that makes it real is the record-count equality,
not the absence of an error log.

**S-IOT-02, ordering across an outage.** Same outage, but the assertion is placement rather than
count. Build an I-MR chart over the window spanning the outage from the historian and assert the
point order equals the ground-truth sample order. Ordering by `ingest_ts` puts hour-old data after
fresh data and the chart is wrong, so the failing observation is a chart whose point order differs
from the truth order by even one position.

**S-IOT-03, overflow is bounded and admitted.** Extend the outage past buffer capacity. Assert:
`sf_dropped_records` is non-zero and equals the ground-truth count of suppressed records exactly;
the counter reaches the fleet as a Sparkplug metric on the next NBIRTH; the historian's gap
accounting matches the counter; and no downstream statistic is computed over the gap without the
gap being declared.

**S-IOT-04, the clock breaks the certificate, not the certificate.** Drive `clock_drift_ppm` until
the device clock crosses `notBefore`. Assert: the ladder classifies `tls_notbefore` rather than
`tls_expired`; the agent enters `TIME_SYNC_WAIT` rather than looping on handshake failure; the
resync step opens a new `clock_epoch_id`; and the runbook the signature resolves to names the
clock, not the certificate.

**S-IOT-05, crash loop and brownout.** Inject `brownout_crash_loop` on a device transmitting above
the power threshold. Assert: `boot_count` rises inside `crash_loop_window_s`; `crash_loop` is
raised with its severity floor of 8; the brownout correlation signal fires inside
`brownout.tx_window_ms` of a qualifying transmit; the heap signal does not fire, because
`free_heap_min_bytes` is flat; and the generated runbook's fix names supply decoupling rather than
firmware.

**S-IOT-06, the antenna what-if with a verdict.** Configure `dock3-portal-a` to miss about 4% of
reads through an orientation-dependent cause. Run `whatif.rf.add_antenna`,
`whatif.rf.reaim_antenna`, and `whatif.rf.set_conveyor_speed` on the same seed family with common
random numbers. Assert: each candidate returns a read-rate delta, a cross-read delta, a downstream
throughput delta, and a cost; the statistical seam in 5.30 returns a `lss.test.completed.v1` for
each; the winning candidate's effect-size interval excludes zero; and a deliberately tiny variant
is reported as statistically significant and not practically significant. The search is seeded, so
the ranking is identical across runs, and a differing ranking is the failing observation.

**S-IOT-07, cross-reads at adjacent docks.** Place two portals with overlapping read volumes.
Assert: `iot.rfid.read.groundtruth.v1` records `is_cross_read` on the reads the geometry produced
at the wrong portal; deduplication does not remove them, because they are genuine reads;
`twinflow.rf.diagnose` attributes the pattern to physics rather than to the device; and gating
acceptance on `trailer_presence_loop` reduces the cross-read rate while leaving the true read rate
unchanged.

**S-IOT-08, the bearing trend to a work order.** Inject `F-MECH-BEARING` on a conveyor motor.
Assert: the duty-cycle correction removes the schedule signal, so the trend test is not measuring
shift patterns; Mann-Kendall raises a monotone trend before the raw series does; the Theil-Sen
slope interval is finite; `pdm.prediction.v1` carries a time-to-threshold interval that contains
the true crossing time recorded in `rul.parquet`; and `maintenance.workorder.requested.v1` is
published with a runbook reference once the crossing falls inside the planning horizon.

**S-IOT-09, the canary halts the campaign.** Run an OTA campaign whose image degrades health on
the ring it lands on. Assert: the canary ring soaks; `ota.ring.gate.requested.v1` is published; the
reply arrives inside `fleet.stats.reply_timeout_s`; the gate decides against promotion on the
paired test rather than on a threshold; the ring rolls back automatically;
`ota.campaign.halted.v1` names the failing criterion; and INV-OTA-1 holds at every instant during
the rollback.

**S-IOT-10, the enrollment storm.** Present 300 devices to the provisioning endpoint at once,
including one whose serial is absent from the allowlist, one replaying a used nonce, one with a
revoked birth certificate, one presenting a serial already enrolled under a different key, and one
whose clock sits below the gate. Assert: each rejection publishes
`fleet.enrollment.rejected.v1` with its own `reason` value and its own runbook reference; the
remaining devices enroll with no human step; and the nonces are reproducible across a replay,
because they draw from `fleet.provisioning.nonce`.

**S-IOT-11, the address changes and the identity does not.** Inject `dhcp_lease_loss` mid-run.
Assert: the device's address changes; the certificate-based broker ACL continues to authorise it;
and a control arm configured with an address-based ACL is refused. Two lines of scenario make the
design argument that a paragraph would only assert.

**S-IOT-12, two devices with one identity.** Flash two edge nodes with the same `edge_node_id` and
start both. Assert: `bdSeq` outruns `iot.device.boot.v1` arrivals; the fleet layer records
`bdseq_without_boot`; `duplicate_client_id` is raised; both devices are quarantined and their
publishes are refused by the broker ACL rather than merely ignored; and the config that produced
it is refused at validation in the ordinary path, so this scenario has to construct it
deliberately.

**S-IOT-13, what the edge actually buys.** Run a fixed workload of high-rate vibration channels
through a gateway. Assert: `wire_bytes` equals the summed frame lengths exactly (INV-EDGE-1);
`raw_wire_bytes_equivalent` is computed by encoding the same window one record per frame; the
ratio is written to `artifacts/edge/` with the workload described; the deadband suppression rate
is reported as a measurement rather than as a config restatement; and the raw window is still
fetchable on demand from local retention.

**S-IOT-14, repeated measures for the gauge study.** Run the measurement-system scenario: ten
parts, three appraisers, three replicates, with `provision.device.<device_id>.repeatability` and
`provision.appraiser.<appraiser_id>.effect` supplying the two variance components declared in the
catalog. Assert: the emitted readings carry the declared component structure; the study is
handed to the LSS engine through the ordinary event path; and the components the engine recovers
are scored against the declared ones. This section owns the generator and the declaration; the
study itself belongs to the LSS engine.

**S-IOT-15, QoS 1 without lying about conformance.** Run the same fleet and seed with the UNS
mirror at QoS 0 and at QoS 1. Assert: the business event stream is identical under the documented
normalization; the measured redelivery count at QoS 1 is reported, and it is the number the
`mqtt_redelivery` fault mode inflates. A second arm declares a departure on
`tck-id-payloads-ddata-qos`, publishes DDATA at QoS 1, and asserts `ConformanceMatrix` marks the
run non-conformant and names the rule.

**S-IOT-16, health at t=0.** Start a 500-device fleet with no history. Assert: every device has a
defined `health_score` inside `[0, 100]`; every `fleet.health.scored.v1` carries `prior_used`
naming which prior was applied; `c_i` is multiplied by `prior_confidence_penalty` while a prior is
in use; and the first lifecycle transition happens no earlier than `dwell_s` after the score
crosses its threshold.

**S-IOT-17, the gateway goes dark.** Partition tier 1 from tier 2 for 30 simulated minutes.
Assert: `edge.degraded.v1` lists retained capabilities (safety interlocks, local anomaly flagging,
local store and forward, the line keeps running) and lost capabilities (SPC evaluation, twin sync,
agent answers, cross-area correlation); both lists are generated from the placement table rather
than from prose; the safety interlock latency stays inside its budget throughout; and on
reconnection the spilled records replay in per-channel FIFO order.

### 7.4 External conformance evidence

Two bodies of external evidence carry the two claims a reader is most likely to test: that the
Sparkplug codec is conformant, and that the RF model is more than a curve fit.

#### 7.4.1 Sparkplug B v3.0.0 conformance (E3)

`schemas/iot/sparkplug/conformance.yaml` enumerates every normative rule id the codec claims to
satisfy, with the topic class, the QoS, the retain flag, and a basis string. The file is the
single home for those values, and 5.4's table is checked against it at load rather than restated
in code.

The Eclipse Sparkplug Technology Compatibility Kit is the arbiter for the normative half. The
repo runs it against the reference edge node and host application built from `twinflow-sparkplug`,
commits the TCK result file to `artifacts/tck/` with the date, the TCK version, the git SHA, and
the dependency lockfile hash, and the README cites the committed artifact rather than a claim.
`test_conformance_yaml_covers_tck_result` asserts that every rule id the TCK reports on appears in
`conformance.yaml`, and that no rule id in `conformance.yaml` is absent from the TCK report, so
the two cannot drift. A run holding any entry in `transport.conformance_departures` writes
`conformant: false` into every artifact it produces. See open question 9.1 on the TCK's own
licensing and on whether its results may be redistributed.

#### 7.4.2 The VG-IOT gate registry (E46 and the rest)

Every value this section publishes as an external fact carries a gate record in
`validation/valgates.yaml`, the same registry and the same schema the LSS engine section defines,
so the two sections produce one `docs/VALIDATION.md`. A gate that names no valid external
reference is recorded as an open question in section 9 and never as a passing gate (D-11).

A value this section does not publish as an external fact carries the literal string
`"repo-defined modelling assumption, not a measurement"` in its `source` field instead. Three
checks together leave no third state: INV-RF-6 covers every `PhysicalConstant` in `twinflow-rf`,
the `limit_source` rule of 3.1 covers every catalog channel with numeric alarm limits, and the
per-row `source` rule of 6.12 covers every standalone file holding a physical or regulatory

the `fleet/ap_table.yaml` rows are where that applies, and each has an open question in section 9

literally: the honest count in `docs/VALIDATION.md` is twelve gates with retrievable primary
references, three at single-source confidence, and one open.

### 7.5 Fault coverage and the resilience gates

Coverage over the fault catalog is a test rather than a table that ages.
`test_every_owned_fault_is_injectable` reads `docs/design/variability-and-faults.md` C.4, filters
to the ids this section owns, and asserts that each one has an injector, a detection signature in
at least one catalog entry, a runbook template, and at least one scenario in 7.3 that exercises
it. `test_every_class_has_four_signatures` asserts that each of the twelve signal-model kinds has
at least one shipped catalog entry declaring drift, stuck-at, dropout, and calibration loss, which
is component 2b's requirement that every sensor class carries all four.

Detector scoring uses the matching rule and the metrics in variability C.6 without restating
them. This section adds one constraint on top: `mttd.leakage_is_fatal` defaults to true, so a
detection earlier than `detectable_from_sim_ts` fails the run rather than improving the reported
MTTD. A leakage failure is investigated as a windowing or labelling defect, never accepted.

The `SCN-DEVICE` labelled scenario pack in variability C.7 is the fixed evaluation set for this
section's detectors, and the published precision, recall, and MTTD distribution come from it.

### 7.6 Benchmarks and the artifacts they write

Two jobs measure. Neither is a unit test, both write dated artifacts, and both name the hardware,
because a latency or bandwidth number with no hardware is not a measurement.

**BM-IOT-01, edge latency.** Runs the actual tier-0 and tier-1 code paths over 10,000 samples per
function class with no simulated stage costs, and writes `artifacts/edge/bench_{date}.json` with
p50, p95, p99 per function class, the hardware description, the git SHA, and the lockfile hash. It
fails when a p99 exceeds its budget on the reference runner and reports rather than fails on any
other runner, because a loaded shared runner cannot falsify a latency claim.

**BM-IOT-02, wire bytes.** Captures the serialized length of every frame crossing a tier boundary
and fails when the total disagrees with the sum of the frame lengths the transport adapter
recorded. It is the gate over the measured half of 5.17, and it exists because the computed half,
`deadband_suppressed` and `aggregation_reduced`, is bookkeeping derived from the same config that
produced the filtering and cannot corroborate itself.

The hardware-in-the-loop path has no benchmark, and 5.26 says why. The nightly CI job builds the
`esp32` target and boots it under the Espressif QEMU fork, asserting it reaches `TIME_SYNC_WAIT`
and publishes a valid boot record, which proves the build and the early state machine and not the
radio. `just hil-selftest` is run by a human against real hardware and its output, with the date,
the firmware hash, and the git SHA, is committed to `artifacts/hil/`. The README says exactly
that.

### 8.3 The cost of the Rust and ESP32 targets in CI

5.26 says the CI cost of the `esp32` target is priced here rather than assumed, because the
esp-idf toolchain is not free to provision on a hosted runner. The three jobs and what each buys:

| Job                        | Trigger                    | What it provisions                                        | What it proves                                                                   |
| -------------------------- | -------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `rust-host`                | every pull request         | the stable Rust toolchain, cached                         | the crate builds and its unit tests pass with `--features host`                  |
| `parity`                   | every pull request         | the same toolchain plus the Python environment            | IC-IOT-03 and VG-IOT-02 over the shared corpus                                   |
| `esp32-qemu`               | nightly, and on a tag      | the esp-idf toolchain and the Espressif QEMU fork, cached | the `esp32` target builds and boots to `TIME_SYNC_WAIT` with a valid boot record |

The esp-idf toolchain and the QEMU fork are cached by toolchain version, so the provisioning cost
falls on the first nightly after a version bump rather than on every run. The job is off the
pull-request path deliberately: a contributor changing a catalog YAML file must not wait on an
embedded toolchain. C10's stated CI wall-time budget covers `rust-host` and `parity` on
the pull-request path, and `esp32-qemu` is budgeted separately as a nightly.

None of the three proves the radio. `just hil-selftest` is the only thing that does, it is run by
a human, and its committed output in `artifacts/hil/` is what the README cites.

## 9. Open questions

These are genuine ambiguities in the source, genuine conflicts between locked decisions, or
claims whose primary evidence could not be retrieved. None has been resolved by invention, and
none of them is a requirement that has been dropped.

**9.1. What arbitrates a QoS conformance departure, and may the TCK result be redistributed?**
5.4 makes every Sparkplug QoS and retain value normative and read from the specification, and
`transport.conformance_departures` is the only legal way to depart. Two things need the author's
decision. First, whether a departure is permitted at all in a shipped profile, or only in
a test arm such as the second arm of S-IOT-15; the spec currently permits it anywhere with a
named rule id and marks the run non-conformant. Second, whether the Eclipse Sparkplug Technology
Compatibility Kit's result file may be committed to a public repository, which depends on the
TCK's own licence and was not settled here. If it may not, 7.4.1's committed artifact becomes a
summary rather than the raw result, and the README claim changes accordingly.

**9.2. An EPL-2.0 file vendored into an Apache-2.0 repository with a commercial option.**
`sparkplug_b.proto` is vendored under its own EPL-2.0 licence into `schemas/iot/sparkplug/`,
recorded in `THIRD_PARTY_NOTICES.md`, and excluded from the Apache-2.0 relicensing sweep. EPL-2.0
is a file-level weak copyleft, so vendoring one file and keeping it under its own licence is the
ordinary arrangement, and the generated Python module derived from it inherits the question. This
needs the owner's own legal read before release, on the same footing as D-14's note about PM4Py
as a development-only oracle. The alternative is to generate the codec from a hand-written schema
that is not a derivative of the Eclipse file, which costs work and loses the guarantee that the
wire format matches the specification's own definition byte for byte.

**9.3. Can the AIAG and VDA Action Priority table be reproduced lawfully?** 5.13 ships
`fleet/ap_table.yaml` as a repo-defined table with its own documented derivation rule, and makes
no claim that it matches the published one. The handbook is a paid publication and its page
returned HTTP 404 on 2026-08-09. Two options. Transcribe the published lookup, which is a factual
table of 1000 rows and is the kind of thing that may or may not be copyrightable depending on
jurisdiction, or keep the repo-defined table and document the difference. The spec assumes the
second. An adopting organisation with its own licensed copy replaces the file.

**9.4. Do the shipped profiles default to one edge node per line or one per device?** 4.1
defaults `edge_node_id_template` to `{line}`, so one agent process per line hosts every device on
that line, and offers `{line}-{equipment}` for a deployment that wants one process per device.
The first is what a real gateway-fronted fleet looks like and it is cheaper in sessions. The
second matches the mental model of most readers, who expect a device to be an MQTT client. The
demo's legibility argues for the second and the architecture argues for the first. The three
worked profiles from A2 could reasonably differ from each other here, and the author picks
which default leads in the README.

**9.5. Which broker does CI run, and which one does the README quickstart name?** A3 names three
tiers and 2.1's `Network` port has adapters for Mosquitto, EMQX, and NanoMQ. 6.6 puts NanoMQ at
the gateway and 5.16 puts EMQX at the site, which is a two-broker topology in the compose file.
Running all three in CI triples the container job. Running one leaves the other two adapters
untested against a real broker. The adapter conformance suite splits by port under D-08, so the
question is which of the three is the one CI must always run, and whether the other two run
nightly.

**9.6. Is 191 channels across 80 entries the right shape?** 3.2 sums to 191 channels, an average
of 2.4 per type, ranging from one to six. That number drives the Sparkplug alias table size, the
UNS topic count, the historian's column count, and the load-time budget in 6.2. A reader might
reasonably expect either a leaner catalog with one channel per type and more types, or a richer
one with more channels per type and fewer. The current shape follows the source's instruction that
each type unlocks a capability, and the capability registry enforces it, but the author confirms
whether 191 is the number the README quotes rather than 80.

**9.7. Does the ground-truth Delta root need protection beyond path separation?** 5.12 puts the
firewall in the physical separation of two Delta roots plus a DuckDB session with
`enable_external_access` off, because delta-rs and DuckDB have no roles or grants. That is
enforceable and INV-GT-1 tests it. It is not a security boundary against a process running as the
same user. Whether that matters depends on whether an adopter ever runs the agent against a
historian holding real labels, which twinflow itself never does because all data is synthetic.
The question is whether to document the limit plainly in SECURITY.md or to add a second mechanism.

**9.8. The MSA variance components are modelling assumptions, not gauge studies.** 3.1 requires
every channel to declare `repeatability_sigma` and `reproducibility_sigma`, and the shipped values
carry `msa_source: "repo-defined modelling assumption, not a gauge study"`. That is honest and it
means the LSS engine's Gage R and R has a declared ground truth to recover rather than a measured
one. VG-MSA-05 in the LSS engine section scores recovery against the declared components, which is
a valid test of the estimator and not evidence about any real gauge. If the author wants a
published gauge reference for even one channel, it would have to come from a manufacturer
datasheet with a stated repeatability figure, and none was retrieved for this spec.

**9.9. Product or weighted sum for the health score?** 5.13 uses
`100 * PROD(1 - min(1, RPN_i / 1000) * c_i)`. The product compounds independent problems, which is
the behaviour the fleet layer wants, and it satisfies the seven properties INV-HS-1 through
INV-HS-7 assert. It also drives the score toward zero quickly when many low-severity modes are
active, which can read as alarmist on a large fleet. A weighted sum with a cap behaves better
there and compounds worse. No external reference governs the choice, so it is a design decision
the author confirms rather than a fact this spec can cite.

**9.10. The cross-platform float tolerance is not yet a number.** D-05 requires the
value-equivalent tier to state a tolerance derived from measured divergence. VG-DET-IOT-03 reports
the observed maximum into a dated artifact and compares it against a recorded tolerance, and that
tolerance cannot be written until the first measurement runs on the supported platform set. Until
then the gate records the observation and does not assert a threshold, which is the honest state
and is recorded here rather than filled with a plausible number.

**9.11. The Schoute paper is behind a paywall.** VG-IOT-12's reference is Schoute, "Dynamic Frame
Length ALOHA", IEEE Transactions on Communications, volume 31, number 4, 1983, pages 565 to 568.
The DOI resolver returned HTTP 202 with an empty body on 2026-08-09 and no full text was
retrieved. The gate is carried at single-source confidence with the attribution stated in text. A
retrieved copy, or a second independent published statement of the `1/e` maximum, would raise it.
The Gen2 half of the claim is unaffected, because VG-IOT-11's reference was retrieved in full.

**9.12. Where do the Mann-Kendall and Theil-Sen reference datasets come from?** VG-IOT-07 and
VG-IOT-08 name Examples 12.1 and 12.2 of the USGS report, whose text and printed statistics were
retrieved, but whose underlying data series were not. The report is a US Government work in the
public domain, so redistribution is not the obstacle; sourcing is. The Big Sioux River series in
Example 12.2 is annual mean discharge from a National Water Information System gage and can be
retrieved by gage number, and the Milwaukee River chloride series in Example 12.1 needs the
report's companion data release. Until both are checked into `validation/data/` with a provenance
line, the two gates are registered as `PENDING` rather than passing.

**9.13. How exactly do twinflow quality codes map to OPC UA status codes?** 2.2 declares
`Quality` as `GOOD | UNCERTAIN | BAD | SUBSTITUTED` and calls it OPC UA style. That is four values
against a specification that defines a 32-bit status code with a two-bit severity and a large
sub-code space. The four-value enum is the right shape for this repo, and calling it OPC UA style
rather than OPC UA compliant is deliberate. What is unresolved is whether the RA(e) OPC UA bridge
at P5 needs a documented total mapping in both directions, which would make the bridge honest, or
whether a one-way mapping into the four values is enough for what the bridge demonstrates.

**9.14. Is 80 the right count, and is `status: planned` ever acceptable?** The source states a
band of roughly 60 to 80 implemented types and gives the reason: the skill on show is the catalog
architecture, not the count. 3.2 takes the top of the band. `catalog.allow_status_planned` is
false in a release build, so a planned entry cannot ship, which means the count is the implemented
count and not an aspiration. If the author would rather the README quote a smaller number with
deeper models per type, the change is deleting entries from category files and adjusting the
counts in 3.2, and nothing else moves.

**9.15. The occlusion losses are modelling assumptions with no measured source.** 5.21 ships
`none: 0.0`, `cardboard: 0.5`, `liquid: 6.0`, and `metal: 20.0` dB per layer, each carrying the
literal string `"repo-defined modelling assumption, not a measurement"`, because no published
measurement series for these materials at 900 MHz was retrieved for this spec. INV-RF-7 asserts
the ordering and the monotone decline in `depth_in_pallet`, which is the part a test can prove.
Replacing the magnitudes with measured values from a named published series would upgrade the
claim from ordering to magnitude, and it is the single highest-value evidence gap in the RF model.

**9.16. Nowlan and Heap could not be retrieved.** The P-F interval concept that grounds the
detection rating in 3.6 and VG-IOT-06 is cited to Nowlan and Heap, "Reliability-Centered
Maintenance", United States Department of Defense, 1978, DTIC accession AD-A066579. The DTIC
record refused automated retrieval on 2026-08-09 with HTTP 403. The citation is carried at
single-source confidence with the attribution stated in text. An accessible primary copy, or a
second independent published statement of the interval's definition, would raise it. The gate
itself does not depend on a numeric value from the source, only on the definition, which is why it
remains a gate rather than becoming an open question outright.

**9.17. The brownout model has no measured board.** 5.9 states the relation
`V_rail = V_supply - I_tx * R_supply` with a threshold, and 6.4 holds all four constants plus a
transmit-current curve, every one of them labelled as a repo-defined modelling assumption. The
model produces the right qualitative behaviour, INV-BRN-1 asserts the causal link the runbook
depends on, and `test_brownout_needs_tx` proves the absence case. What is missing is one measured
current curve for one real board, which the HIL device at P6-W1 could supply and which would turn
the whole model from plausible to grounded.

**9.18. No retrievable reference for the bearing defect frequency formulas.** VG-IOT-10 is
recorded as an open question rather than a passing gate, per D-11 rule 5. The four formulas in
5.14 are standard, and their algebraic consequences (`BPFO == Nb * FTF`, `BPFI > BPFO`) are
asserted internally, but no external published statement of them was retrieved for this spec. The
likely candidates are a bearing manufacturer's engineering reference or an ISO vibration standard,
and the same question covers the `limit_source` for `vibration_velocity_iso`, whose alarm limits
currently carry no external clause either. Until one is retrieved, the README's validated-statistic
count does not include VG-IOT-10.

**9.19. Gen2 Release 3.0.1 against ISO/IEC 18000-63.** 5.22 cites the GS1 EPC Gen2 standard,
Release 3.0.1 of February 2026, whose full text was retrieved. The corresponding ISO standard,
ISO/IEC 18000-63, tracks it at a lag and its page returned HTTP 403 on 2026-08-09, so any
divergence between the two at the parameters this model uses is unverified. The spec cites the GS1
document because it is the one that was read. If the author wants the ISO citation in the README
for the audience that recognises it, the divergence needs checking first, and naming both without
checking would be the kind of citation added after the sentence was written.

**9.20. Does the Rust crate share one version number with the Python bricks?** 2.11 says the crate is
published to crates.io by the same automated release job as the Python bricks, and C9 requires
lockstep versions across bricks. Rust and Python semver conventions differ on what a major bump
means for a pre-1.0 crate, and crates.io yanking is not the same operation as a PyPI release
deletion. The question is whether the crate genuinely shares the version number, which is simple
and occasionally wrong, or carries its own with a compatibility table, which is honest and one
more thing to maintain.
